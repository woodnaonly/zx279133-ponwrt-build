# 109 — 发布线整理收尾：只有 7.3 线发版，远端清成什么样，以及两次 CI 事故的修法

> 本文记录的是**发布线**这一轮：从「两条线都能发 Release」到「只有 7.3 线发版」，
> 以及把 GitHub 上堆积的历史 Release、标签与构件清成可用状态。
> 上游 OMCI 引擎的同步记在 `docs/110-the-upstream-omci-vendor-and-its-drift-lock-20261127.md`。

---

## 判决

1. **7.3 线是唯一的发布线。** 它的标签前缀是 `skd840n_73_`；6.18 线与副线（ponctl、
   sr1010）只构建、只出构件，不进 Releases 页。
2. **远端已经清空成可用状态**：历史 Release 全删（259 个），旧标签删到只剩 3 个
   `archive/*`，构件按名字只留最新的一份。
3. **两件事由门禁盯着，不是靠记性**：哪条线发版（`tools/check-sk-release-line.py`），
   以及发版公告的版本是不是从锁文件里读的（`tools/check-baked-version.py`）。

---

## 1. 两条线，一条发版

改之前，两条线都往同一个 Releases 页上发：

- 6.18 线（`build-sk-d840n.yml`）发 `skd840n_flash_<run>_<id>` 这类标签；
- 7.3 线（`build-sk-d840n-73.yml`）发自己的标签。

两条线的 run 号是各自计数的，所以「run 98」在两边都出现过 —— 页面上分不清哪个
包是哪条线编的。

现在：7.3 线的标签是 `skd840n_73_<mode>_<run>_<id>`，只有它发 Release；6.18 线只
上传构件。判据写在一处：

- `tools/check-sk-release-line.py`：读两个工作流的 YAML，比较**哪个**发了发布步骤、
  标签前缀对不对、发布正文里的文件名是不是这次构建真产出的（对照 run #96 的实测
  清单 `tests/fixtures/sk-73-artifact-files.txt`）、6.18 线的文件有没有混进来；
  还检查工作流调用的每个门禁**在树里**，且**真的接受传进去的选项**。
- `tests/test_sk_release_line.py`：反控，逐条破坏门禁，证明门禁会红。

## 2. 版本不许写进决定

门禁里一度写着 `"7.3.4"`，`tools/check-baked-version.py` 把它点了出来：
**版本写进决定，对一条线是对的，对别的线就是错的**，而且版本一升，门禁与构建就
各说各话。

所以门禁改成从两个锁文件里读：`configs/sk-d840n-73.json`（7.3 线）、
`configs/sk-d840n-stable.json`（6.18 线）。发布正文里必须出现本线的版本，且不许
出现另一条线的版本。

## 3. 两次 CI 事故

**事故一：工作流按 `--tree` 调反控，反控不接受。** 两条线在 gates 作业里死掉，
run 98 与 run 449 都是这么死的。修法是把选项接上，并且给门禁加一条检查：
**工作流调用的脚本必须在树里，而且必须真的接受传进去的选项**（用 argparse 的声明
来核对，不靠文本里有没有出现过这个词）。

**事故二：门禁里写死了版本字面量。** 上面那条。

两次事故的共同点：**门禁自己也要被门禁**。`tests/test_sk_workflows.py` 管着
「工作流有没有丢步骤、工作流有没有还解析得了、路径过滤器有没有覆盖工作流跑的
每个文件」；`tools/check-sk-workflow-paths.py` 管着「工作流跑的文件必须登记在
`paths:` 里」，否则改了它不会触发构建，等于这个门禁从此没人跑。

## 4. 远端清理：删了什么，留了什么

用户拍板的范围：**Releases 全删清空**（含 run 447 那套资产），只保留 3 个
`archive/*` 标签，构件只留两条线每个名字最新的一份。

执行结果：

| 对象 | 清理前 | 清理后 |
|---|---|---|
| Releases | 259 | 0（随后 7.3 线自己的首个 release 占了 1 个） |
| 标签 | 747 | 3 个 `archive/*`（`tcp-control-perf`、`tcp-optimized-perf`、`tproxy`） |
| 构件 | 1098 | 每个名字最新的一份（10 个） |

需要留意的两点：

- **删 release 不会自动删 git tag。** 两个是分开的东西，要分别清。
- 746 个待删标签里，**282 个是其旧构建提交的唯一引用**（那些提交不在 main 的
  历史里）—— 删掉之后，那些旧构建快照就不可达了。这是清理的代价，记在这里。

清理脚本在 `scratch/cleanup_releases.py`（仓库外）。两个坑记一下：标签清单要用
`GET /git/matching-refs/tags/`（`/git/refs/tags` 那个 340 KB 的响应会挂死，而且
不支持分页）；构件端点返回的是对象，取 `["artifacts"]`。

## 5. 现状

- 7.3 线的 **run #100 首次发版成功**：
  `skd840n_73_initramfs_100_45844120540`，带三个资产
  （`immortalwrt-zte-zx279133-rootfs.cpio.gz`、
  `immortalwrt-zte-zx279133-skyworth_sk-d840n-initramfs.itb`、`sha256sums`）。
- 构件会随着每次推送增长；**发版完成一轮之后要按名字再清一次**，只留最新的一份。

## 6. 没做的事

- 8 个 fork 的残留分支没清：本机凭据属另一个账号（`44451516`），对本仓库只有
  pull 权限，删不了。需要仓库所有者自己删，或授权。
- **没有推任何标签**：推标签会触发构建，整理阶段不推。
