# The 9132's ERAM tables: where they really are, and what the console does to your numbers

*2026-10-21, after run111..run115*

Everything in this file was measured, not assumed.  The two things that cost
the most time were both about *numbers*:

* the address of a table, and
* the number the console wrote into it.

## 1. The table list is the vendor's, item for item

The ERAM is a flat pool of 128-bit blocks that starts at block 0x1000, and
the hardware is told where every table lives by a list the driver writes into
the switch's SDT registers.  If the driver's list is not the vendor's list,
every table is written at the wrong block and the hardware reads the blocks it
was told about and finds nothing there.

The vendor's list is `g_core_sdt_info` in np_133.ko: 53 entries, each
`{ id, type, p3, count }`.  The driver now uses exactly that list, followed by
three tables of its own (0x00, 0x04, 0x06), which the vendor's list does not
have.

The allocation is the vendor's own, out of `se_smmu0_reg_table()`:

    eram_base = 0x3000
    for each table:
        bit_len = { 1, 32, 64, 128, 2, 4, 8, 16 }[p3 & 7]
        depth   = (bit_len * count + 127) >> 7
        base    = eram_base
        eram_base += depth

**The pool starts at block 0x3000, and that is the whole ball game.**  The
ERAM is a window into the switch chip, and below 0x3000 there is no window:
the address lands somewhere else, and what comes back is the SoC's own
memory.  The board says so in one line.  Write a word into a block and read
it back:

    eram block 12000 = 00b91a7f 40000000 00b91452 40000000
    eram block 12288 = deadbeef 11111111 22222222 33333333

The first is a page table entry out of the SoC's RAM - the write did not
land, and the read came from somewhere else entirely.  The second is the
word that was written, read back unchanged.  The boundary is exactly 0x3000,
and at the top the ERAM ends at 0xc000:

    eram block 45056 = deadbeef 11111111 22222222 33333333
    eram block 49152 = 00000000 00000000 00000000 00000000

So the ERAM is [0x3000, 0xc000), the tables live in [0x3000, 0x9000), and
the statistics have [0x9000, 0xc000) to themselves.

The driver had been allocating its tables from block 0x1000.  Every one of
them was therefore 0x2000 blocks below the ERAM, and the hardware - which
reads the tables where the driver told it to - found nothing there.  The one
table that was written high enough to land (0x7d, whose base came out at
16545 by accident) did come back exactly as it was written, which is how the
mistake survived so long: one table out of fifty looked right.

`staging/ctl/eramplan.py --map` prints the result.  The tables this work
touched:

| table | what it is            | base block | bits per entry | blocks |
|-------|-----------------------|-----------:|---------------:|-------:|
| 0x18  | protocol action       |      16416 |              2 |    128 |
| 0x19  | reason map            |      16544 |             32 |     64 |
| 0x22  | global config         |      16384 |            128 |     32 |
| 0x1b  | isolation matrix      |      16612 |              1 |     32 |
| 0x23  | output VLAN check     |      16652 |              1 |      1 |
| 0x24  | port bind             |      16653 |              1 |      1 |
| 0x25  | port PVID             |      16695 |             16 |      8 |
| 0x27  | outport map           |      20801 |             16 |      8 |
| 0x7d  | MF extension (ports)  |      21467 |            128 |     64 |

**Confirmed on the board.**  A trial kernel built from run113 was read back
through the driver's own console (`er <block> 1`), and it holds exactly
this - at the run113 bases, which are 0x2000 blocks too low:

    eram block 28044 = 00000000 00000000 00000000 00000000   <- run111's wrong base, now empty
    eram block 22834 = 00000000 00000000 00000000 00000000   <- run111's wrong base, now empty
    eram block 16482 = 00000000 00000000 00000000 00000000   <- run111's wrong base, now empty
    eram block 16545 = 00060000 00000000 00000000 00000000   <- 0x7d entry 0: the attribute word
    eram block 16546 = 96040001 00000000 00000000 00000000   <- 0x7d entry 1: a UNI jack
    eram block 16550 = 96040001 00000000 00000000 00000000   <- 0x7d entry 5: the CPU port

So run112's list and run113's attribute-word move are both right, and the
boards' old bases are empty: nothing is written to the wrong place any more.

## 2. The console reads a bare number as decimal, or as octal

The driver's console commands parse their arguments with `kstrtou32(tok, 0,
&value)`.  A base of zero means "guess": a `0x` prefix is hexadecimal, a
leading `0` is octal, and anything else is **decimal**.

That means a value written on the console as `ew 16546 96040001 0 0 0` does
not put 0x96040001 into the table.  It puts the decimal number 96040001 into
it, which is 0x05b97441.  And `ew 16546 00060000 0 0 0` puts the *octal*
number 60000 into it, which is 0x00006000.

This is not a theory; it is what the board said, three times over:

| written on the console | what the board read back | what it really was      |
|------------------------|--------------------------|-------------------------|
| `96040001`             | `05b97441`              | decimal 96040001        |
| `00060000`             | `00006000`              | octal 60000             |
| `00040000`             | `00004000`              | octal 40000             |
| `00042000`             | `00004400`              | octal 42000             |

Every value on the console carries a `0x` prefix now.  The driver's own
writes are not affected: they are C constants.

## 3. What is still missing, and how the trial kernel was made to talk

The ERAM is DRAM: it comes up empty after a power cut, and the vendor fills
it in during its own load path.  A driver that leaves a table alone leaves it
empty.

run113 writes the 9132's port attributes (0x7d) and the switch's protocol
action table (0x18).  It does not write the three tables that say where a
frame the switch hands to the CPU goes:

| table | what the vendor writes there                         | where it goes            |
|-------|-------------------------------------------------------|-------------------------|
| 0x22  | the CPU base queue id 0x193, the mul ip mode, the ipv6 crc32 mode | entry 0, word 3, bits 17..25 / 13 / 16 |
| 0x27  | outport 15 (the CPU's own outport) is the real port 15 on queue 0x193 | entry 15, 16 bits: port in bits 0..5, queue in bits 6..14 |
| 0x19  | reason 0 (OMCI) is delivered to CPU queue 7           | entry 0, word 0, bits 24..28 |

and the three tables that decide whether a port may talk to another port and
whether a frame is checked for a VLAN on the way out:

| table | what the vendor writes there                         | where it goes            |
|-------|-------------------------------------------------------|-------------------------|
| 0x1b  | the whole 64x64 matrix: the diagonal is 1, the rest 0 | index src \| (dst << 6)  |
| 0x23  | 1 for ports 0..7 and 0x10..0x30                      | one bit per port         |
| 0x24  | 0 for all 64 ports                                    | one bit per port         |
| 0x25  | 0 for ports 0..7 and 0x10..0x30 (a transparent bridge has no PVID) | 16 bits per port |

Every one of those values comes out of the vendor's own code - the setter
that writes it, and the live board that has it - and not out of thin air.

## 4. How the experiment was run

The trial kernel's only way in from the PC is the 9132's LAN path, which is
exactly what is broken, so the experiment is run over the serial console:
`staging/ctl/eramplan.py` writes the tables the vendor writes, at the blocks
the 53-item list says they belong at, and `staging/ctl/autopatch2.ps1` waits
for a trial kernel to appear, writes the tables, and reads the counters back.

The board's power is cut every ninety seconds or so, and the console is a
115200 baud line into a busybox shell, so:

* the whole patch is one short line, with the tables that repeat written by a
  shell loop, because a patch that has to be sent as three lines can straddle
  a power cut and lose the first of them;
* every command is short, because the console drops characters when a long
  line arrives faster than the board can read it, and a dropped quote leaves
  the shell waiting for the rest of the command - after which every later
  command is swallowed and the console looks dead.
