# ME 表写不进去：根因、证据与厂商侧对照（2026-11-01）

> **⚠ 2026-11-01 晚间订正（同一晚，见 docs/99 §1.2 / §1.3 / §7.1）**
>
> 本文 §0 的解释**已被同一天的实测推翻**。仍然成立的部分是**现象**：
> `mes` 写不进去、CPU 写进去的值一次都没出现过。
>
> 被推翻的是**归因**：那 16 个字（`PPS+0x90350` 起）**不是**「flow → ME 分派表
> 在 CPU 侧的只读镜像」，**也不是一张表**：
>
> - `0x902c0..0x9041c` 整整 88 个字读出来**永远是同一个值**，且随时间自己变；
> - 那个值恰好就是 cluster 的 **INST_LO / INST_HI**（`0x90d0c` / `0x90d10`）的两个半字
>   （实测同时读到 `0x00000180` 与 `0x00180000`）；
> - 厂商描述符表里指向 `0x90350` 的**唯一一行**（id 67）自己就声明 `type = 1`（只读）；
> - 而「厂商给同一地址发两个 id」是**重建**出来的假象 —— 出厂二进制里只有 id 67 一行，
>   id 66 那一行是**全零空洞**（访问层没有终止符逻辑，见 docs/99 §7.1）。
>
> ⇒ **`PPS+0x90350` 是 cluster 指令寄存器在窗口里的别名，不存在「ME 表」这个东西。**
> 下文所有「表」字都应读作「那个只读状态寄存器」。
> 详见 docs/99 §1.2（实测）、§1.3（结论）、§7.1（厂商侧完整对照）。
>
> 引擎分派真正的落点因此仍然不在这个寄存器窗口里 ——
> 但它也不在 **blob 的 64 条 PORT_FLOW（tag 0xbbbbbbbb）** 里：
> 那 64 条给的是「端口 → flow」，不是「flow → 核」（docs/99 §1.1）。

## 0. 一句话

`mes`（写 ME 表）在运行期**写不进去**，而且不是驱动算错了位、也不是地址错了：
**PPS 窗口里 ME 表那 16 个字不是 CPU 可写的配置寄存器，而是 PPU cluster 自己那张
「flow → ME」分派表在 CPU 侧的只读镜像。** CPU 写进去的值在任何一次采样里都没有
出现过；同一窗口的邻居寄存器（pkt-type detail，0x9045c）却是写进去就能读出来的，
所以「PPS 窗口整体只读」这个解释也被排除。

引擎分派真正的落点因此不在这个寄存器窗口，而在 **PPU 微码 blob 里的 64 条
PORT_FLOW（tag 0xbbbbbbbb）**。

---

## 1. 现象

2026-11-01 的两次冷启动（同一块板、同一个 run 300 内核）：

```
# 12:17 那次
[    0.441393] ppu: factory ME word 0 = 0x00000000      <- probe 读到的出厂值
[   54.923573] pps reg 0x090350 = 0x00000001            <- 运行期
# mes 7 3 / mes 4 3 / mes 0 2 写完立刻读回，仍是 0x00000001

# 12:41 那次（U-Boot 里手工 run bootcmd 起的那次）
[    0.441393] ppu: factory ME word 0 = 0x00000000
[   82.969304] pps reg 0x090350 = 0x00000000            <- 运行期还是 0
[  103.840363] pps reg 0x090350 = 0x00000000
[  123.888879] ppu me word 0 = 0x00000000               <- mes 0 2 自己的回读
[  124.892934] pps reg 0x090350 = 0x00000001            <- 整表被异步改成 1
[  152.696328] pps reg 0x090350 = 0x00000001
[  153.699013] ppu me word 0 = 0x00000001               <- mes 0 2 写 2 之后的回读
[  154.702964] pps reg 0x090350 = 0x00000001
[  156.705535] pps reg 0x090350 = 0x00000001
[  159.708196] pps reg 0x090350 = 0x00000001
```

要点：

1. **写进去的值一次都没出现过。** 往 word 0 写 `0x00000002`，之后 1 s / 2 s / 3 s /
   6 s 四次采样，寄存器恒为 `0x00000001`；`mes` 动词自己在写完之后立刻回读，也是
   `0x00000001`。写 0 同理（表当时本来就是 0，看不出差别）。
2. **表内容会被异步改写。** 12:41 那次冷启动里，表在 t≈124 s 从「全 0」变成「全 1」，
   而 CPU 从来没有往这 16 个字写过 1（probe 阶段写过，那是唯一一次，发生在 t=0.44 s，
   结果两次冷启动的运行期取值并不一致：一次全 1，一次全 0 到 124 s 才变全 1）。
   → 这 16 个字的内容由 cluster 决定，不由 CPU 决定。
3. **不是「PPS 窗口整体只读」。** 同一窗口的 `0x9045c`（pkt-type detail），
   probe 时读到 `0x00000000`、运行期读到 `0x00000001`，而驱动在 probe 里写的正是 1
   ⇒ **CPU 的写在这个窗口里是生效的**。12:41 那次冷启动的 probe 打印
   `factory pkt-type detail = 0x00000000`（上次冷启动是 1），说明这次是干净的复位值，
   写 1 之后运行期读到 1 —— 写进去了。

## 2. U-Boot 侧：这条线只能证明「U-Boot 映射只读」，不能判定硬件

板子停在 U-Boot 提示符时（2026-11-01 12:39～12:41）：

```
=> md 0x18090350 0x8
18090350: 00000000 00000000 00000000 00000000    ................
18090360: 00000000 00000000 00000000 00000000    ................
=> mw 0x18090350 0x12345678 1
=> md 0x18090350 1
18090350: 00000000                               ....
=> mw 0x1809045c 0x12345678 1
=> md 0x1809045c 1
1809045c: 00000000                               ....
```

复位态 ME 表全 0 ✓（与驱动打印的出厂值一致，地址 0x90350 由此独立得到确认）。
但 **写不进**：ME 表写不进，连 Linux 侧明明能写成功的 `0x9045c` 也写不进。

⇒ U-Boot 这套 U-Boot 把 PPS 窗口映射成了只读（`md` 能读、`mw` 不落），
   所以 U-Boot 无法用来判定这组寄存器在硬件上是否可写。**这条线是负结果，不作数。**

## 3. 厂商模块对照（np_133.ko，反汇编）

工具（自建，在 `staging/ctl/`）：`dis-me.py`（按符号名反汇编）、`reloc.py`
（把重定位解成符号名，`--find` 反查引用点）、`dump-regdesc.py` / `scan-regdesc.py`
（28 字节一行的描述符表）、`disrange.py`（任意地址区间反汇编）。

### 3.1 地址与位布局：我们的常量是对的，而且有两处独立印证

`ppu_cluster_reg_table`（.data 0xc820，68 行 × 28 字节）的第 67 行：

| 字段 | 值 |
|---|---|
| id | 67 |
| type | 1 |
| base | 0x240d4 |
| mask | 0xffffffff |
| shift | 0 |
| max_offset | 8 |
| stride | 1 |

`base` 是**字索引**，字节偏移 = `0x240d4 * 4` = **0x90350**，与驱动的
`ZX279133_PPU_CLUSTER_ME_TABLE` 一致 ✓。

位布局与厂商的 `ppu_cluster_set_me_val_by_flow_num`（.text 0x829dc）逐位一致：

```
w23 = flow_num >> 2                       <- 字
w2  = ubfiz(flow_num, 3, 2) = (flow&3)*8  <- 位偏移
val = (read_word & ~(0xff << shift)) | (me_val << shift)
```

即 16 个字 × 每字 4 个 flow × 每 flow 8 bit = 64 个 slot，与驱动的
`zx279133_ppu_set_me_val()` 完全一样 ✓。

### 3.2 厂商的访问层

`np_onu_reg_read(x0=id, x1=out, x2=index, x3=表, x4=模块号)` /
`np_onu_reg_write(同)`：

```
x19 = 表 + id * 28
if (row->id != id)        return 1;     // id 必须等于行号
if (row->type == 2)       return 1;     // 2 = 只读
if (index > row->maxoff)  return 1;
reg = row->base + index * row->stride;
fpga_read_reg / fpga_write_reg(reg, value, 模块号)
```

模块号 1 = PPS，`fpga_pps_read_reg/write_reg` 的落点是
`ldr/str w, [pps_base + reg * 4]`（reg 是**字**索引）—— 与我们直接 `readl/writel`
的做法等价，**厂商这一侧没有多出「提交 / 生效 / 刷新」之类的步骤**。

### 3.3 厂商那条「运行期改分派」的路径自己就够不着这张表

| 厂商函数 | 传的 id | 表里对应行 | 结果 |
|---|---|---|---|
| `ppu_cluster_set_me_val_by_flow_num` | **0x42 = 66** | 第 66 行 = **整行全 0 的占位行** | `row->id(0) != 66` → 直接返回错误，**打不到 ME 表** |
| `ppu_cluster_set_me_select_en` | 0x31 = 49 | 第 49 行 id 字段写成 **47**（与第 47 行重复），base 0x24117 → 0x9045c | `row->id(47) != 49` → 同样被拒 |
| `ppu_cluster_set_ikey_rsp_fifo_afull_cfg` | 0x2b = 43 | 第 43 行 id=43、base 0x2410f → **0x9043c** ✓ | 与驱动的 `ZX279133_PPU_IKEY_AFULL` 一致 ✓ |

⇒ 28 字节行、`base` 是字索引、`id` 必须等于行号这套解释，由 ikey 那一条独立坐实；
   而 ME 表的描述符在**第 67 行**，厂商自己的赋值函数问的是**第 66 行**。
   换句话说，**厂商模块里那条 tm_debug「运行期改 ME」的功能在这份 np_133.ko 里
   本身就够不着这张表**，我们没有可抄的写协议。

### 3.4 厂商知道 PPS 会在某些状态下不可访问

`fpga_pps_read_reg` / `fpga_pps_write_reg` 的第一件事是读全局 `pps_power_off_flag`，
**为 1 就直接返回，一个字节都不碰**（写路径是 `str w,[pps_base+off]`，读路径是
`ldr w,[pps_base+off]`，都在这道闸门后面）。也就是说厂商自己预期「PPS 有时会锁住」，
并用一个软件标志把这种情况挡在门外。我们的驱动没有这个标志，也没有对应的硬件动作。

## 4. 结论

1. **地址对、位布局对。** ME 表在 PPS+0x90350，16 字 × 4 flow × 8 bit，
   由厂商描述符表和厂商赋值函数两处独立印证。
2. **但这 16 个字在运行期不接受 CPU 写。** 写进去的值从未出现在任何一次采样里；
   而同一窗口的 0x9045c 写进去就能读出来 ⇒ 不是「窗口只读」，是「这张表只读」。
3. **表内容由 cluster 决定。** 12:41 那次冷启动里它在 CPU 没写过 1 的情况下从全 0
   变成全 1，说明这是 cluster 自己的分派表在 CPU 侧的镜像（只读）。
4. **厂商那条运行期改分派的路径在本模块里也是死的**（id 66 落在全 0 的占位行），
   且厂商代码里没有额外的「提交」步骤可抄。

⇒ **`me`（可观测）成立；`mes`（可编程）在这颗芯片的这组寄存器上做不到。**
   引擎分派真正的落点是 **PPU 微码 blob 里的 64 条 PORT_FLOW（tag 0xbbbbbbbb）**，
   也就是「改 blob」，不是「写这个窗口」。

## 5. 下一轮可以做的事（本轮没做，因为要动驱动、要重新出 CI）

1. **加一个受控的 PPS 写入口**（例如只允许写 0x90350 / 0x9045c / 0x9043c 三个已确认
   安全的寄存器），在同一窗口上做 A/B 对照，直接判定「整表只读」还是
   「cluster 起来之后加锁」。这一步能把 §4.2 与 §4.3 之间的余量一次性钉死。
2. **在 probe 阶段写一个可区分的值并立刻回读**（现在是写 0x00000001 后不再回读）。
   若 probe 写完立刻能读到、稍后被 cluster 覆盖成 1，说明「写只在 cluster 启动前
   有效」，那「可编程」的正确时序就落在 probe 期，`mes` 应当改成只在启动前可用。
3. **若目标是运行期改分派**：改 blob 的 PORT_FLOW 注入（在
   `zx279133_ppu_mcode_prepare()` 里按 tag 0xbbbbbbbb 改写 64 条 flow→ME），
   而不是写 0x90350 这个窗口。
