## 0. 目标、范围、非目标

**目标**：让面板上那只标着 LAN1 的 RJ45 在**冷启动 + mainline 6.18.38 + ImmortalWrt** 下自动可用——灯亮、链路 up、PC 能经它拿到板子的网络，**不依赖串口、不依赖人工干预**。

这条目标是**可用性目标，不是带宽目标**。今天被证明能跑通的是 **1000BASE-X 档**（loader 配好的那次启动，PHY 侧 `0x7580` 低 6 位 = `0x02`，`ping 192.168.9.1` 4/4）。**2.5G 是 M5 之后的独立目标**，不要把它写进 M1–M4 的验收，否则“能用”会被“没到 2500”误判成失败。

**为什么先做它**：板子上只有 LAN1 插了 PC。它不通，就等于板子彻底没有网络通道，所有后续工作（9132 转发、PON）都只能靠串口做，一轮只有 20 分钟。

**非目标**：
- **本轮不做 9132 硬件转发**。原请求（LAN↔LAN 不上 CPU）挂起，不是取消，见 §9。它对 LAN1 可用没有任何帮助，而且它的判据需要 LAN1 通才能测。
- 不动 `root` 分区、不做 zrec 恢复、不改 bootargs 之外的 U-Boot env。
- 不在本机编译。CI 是唯一编译通道，push 即触发构建。
- 不把 `eth0` 绑到 XMAC1 之外再猜一次拓扑；`0x140000`（XMAC0）承载 LAN1 已由计数器证明（docs/92 §96.47 的 A→B→A 字节对照）。

**差分已完成的部分（PHY 侧 17 个字 + 近端 7 个 xmac0 字 + 4 个 nppt 字）**
- `devad 0x1e` 的 `75f3 / 697a / 6a04 / 6f10 / 6f11`：**两态完全相同**（0x0002 / 0x0000 / 0x0403 / 0x084a / 0x0021）。
- `7580 7581 7587 7588 7589 758b`、`devad 7:00/01`、`devad 1:00`、`devad 0:00/01`：**两态完全相同**（除 `7580`）。
- `xmac0` 七个字（tx/rx/frame/mode/duplex/misc/send）：**两态完全相同**；`mode` 在 1650 次采样里恒为 0，§96.46 的 `MODE_CFG` 假设已因此作废。
- 只有三处不同：**远端 `0x758d` 0x0010 → 0x801e**、**近端 `nppt 84` 0 → 1**、**近端 `nppt 90` 0x280b → 0x2c03**。

⇒ 结论（判决 AM）：**这不是“少写了哪个寄存器”，是“少了一个状态迁移”。**

**已实测到的那个迁移**：`m45w 5 0x7 0x00 0x3200`（devad 7 reg 0 现值 0x3000，置 bit 9 = restart AN）把 `0x7580` 从 `0x9412` 拉到 `0x9402`，**重复两次成立**。driver 现在从不 restart AN，所以 PHY 从不重新锁存档位。

- 21:06 在活的启动里补抓了正确块的 73 个字：`staging/ctl/lan1-uni-working.clean`。
  `python staging/ctl/uni_profile_diff.py staging/ctl/lan1-uni-working.clean` →
  **`zx279133_uni_1g_profile`：0/49 word(s) differ**，`mode` 字（`0x16100054`）= `0x00000101`。
  即：活的那次启动，Uni SerDes 就是驱动里那份 base-X image 本身。
- 死态的对应抓取由 `tools/lan1waitdead.sh`（后台 b64hyy2tz）在下一次自动断电后写入 `staging/ctl/lan1-uni-dead.clean`。

**这条差分的两种结果都已经值得，写清楚以免下轮误读**：

**⇒ 2026-10-30 21:13 实测，落在第一种分支，而且比预期更彻底**（docs/92 §96.49.2）：死态也是 **0/49**，两态的 49 字 image 完全相同（mode 字都是 `0x101`）；差异全在 image **之外**的 13 个模拟前端/CDR **结果**字上（`0x161000e8` 死=0 / 活=`0x78b2b41c` 这种形状）。

**⇒ 2026-10-30 21:16 M2 的第一个结果**（docs/92 §96.49.4/5）：`socw 0x16100054` 抠 enable bit 再放回 + AN restart，**第一次在 mainline 冷启动里把 `758d`/`7580`/`nppt 84`/`nppt 90` 四个 witness 全部扳到活态值**——但 `pcrxwatch` 的 `rx_delta=0`、板 `eth0` 的 `RX bytes` 恒 0、`TX` 持续涨 ⇒ **板子的 TX 计数是软件计数，帧没上线**。归因因此改成**编排顺序**：datapath 是在 lane 还死的时候 arm 的，lane 复活不会让它重做（`ip link set eth0 down/up` 实测不重做）。

## 5. M2 — 板上复现那一步（每窗口一个动作，按优先级排队）

**判据（M2 的硬判据，两条都要）**：在**一次 mainline 自己配起来的冷启动**里，
(a) `758d=0x801e`、`nppt 84=1`、`nppt 90=0x2c03`；**并且**

> `mode_eth_1gbase_x_cfg` → `uni serdes init succeed` → 1000M full-duplex）。用 trial/initramfs
> 跑出来的 witness 全对，什么也不能证明。
> ⇒ **G3 必须是 flash 分区里的那次启动**：`staging/trial/skd840n_flash_286_41068140744/` 的
> `flash-uImage` + `flash-dtb.bin`，用 `tools/flash-direct.sh` 从运行中的系统写（dtb 先、kernel 后），

**11:19 另取了一份「带 IP 层的前基线」**（存 `staging/ctl/lan1-before-20261031-1119.clean`，5 052 B）：同一台板子、uptime 143.59 s 时，

RTL8226 只被 `lane_watch` 用 MDIO 旁路操作）。⇒ **G4 判据停在 `ping 4/4 + ssh 登录`，不要加「lan5 carrier=up」**；

**由此改掉的两条**：
1. §3 与 §7.9 里「G3/G4 需要机主给一段 ≥2700 s 的连续台面」——**作废**。边沿自动来，`ARM=1` 的 `PROMPT_WAIT=1500 s` 正好盖住最长 20.5 min 的等待。
2. 「请机主切电」这一步**不需要了**；机主只需要给**一句话**（waiver 的原话）。签完之后整条链可以无人值守跑完：

```

        （条件步：第 1 轮若给 acceptlan1 rc=2 —— ping 通而 ssh 是 Permission denied —— 才跑一次 sh tools/serialkey.sh，然后占下一个边沿重跑）
```
**`serialkey.sh` 在 12:2x 被排成必跑的第 3 步、12:5x 又降回条件步**（原因见 §7.12 开头那张表：板上那份 root 里
逐字节命中 4 次的就是本机 `~/.ssh/id_onu`，`sk-d840n-flash-operator` 是 0 命中 ⇒ 10-20 那次修复装进去的钥匙一直活着，因为 root 从没被擦）。
当时把它排成必跑的理由仍然成立、也仍然**只在 rc=2 时才成立**：板子信的钥匙若不是本机这把，`lan1rounds.sh` 的两轮都会是 rc=2，
看起来像「#287 让 ping 通了但 G4 不成立」，其实一句判据都没说到板子。`lan1rounds.sh` 对板子严格只读（不进 `sercmd.txt`），
所以这一步不能并进它自己，只能排在它外面按需跑。
⇒ 无人值守整条链因此是 **3 个边沿 ≈ 61 min**（多出来的第 4 个边沿只属于「钥匙真的丢了」那条支路），
**`lan1rounds.sh 2` 现在自己会拒绝跑错镜像**（12:42 补，docs/92 §96.68）：它要求捕获里**本轮的** `mk=FLASH-START-287` 之后
跟着 `mk=DONE-dtb` 与 `mk=DONE-kernel`（`DONE-` 排在 read-back crc 之后，所以这就是「#287 真上过板」的凭据），否则 **rc=1 硬停**。
补这条的理由是判据完整性：不加门，它会观察两次 pre-#287 的冷启动并打印 `G4 NOT met - 0 of 2`，而那一行会被读成对 #287 的判决。
读法从此三分：**rc=1 = 镜像不对 / rc=2 = 捕获里没等到启动 / 跑完两轮的 `G4 PASS|NOT met` 才是判据**。
**为什么无人值守这条路签 `dtb kernel` 而不是 `kernel`**：`ubflash.sh` 在**擦之前**就把 `STAGES` 定死（[:189-197](../../tools/ubflash.sh)），
它的 `stage()` 里没有「已相等就跳过」，所以 §7.9 第 5 步那条「先读回 dtb 再决定缩窄」**在无人值守的流里根本没有做决定的位置** ——
它只在有人守着 `=>` 时才成立。dtb 那一段本来就已被 §7.10（二）证明与 #287 相同，再擦写一次是一致字节的 13 KB 重写在换一次窗口 vs. 一次多余擦写之间的取舍，
按「结果要在断电前落盘、边沿不能催」这条，选**多擦一段、少一次 stall**。root 不在 `stages=` 里，这条不变。

**两轮 G4 也不要人守着边沿**（10:5x 补，[tools/lan1rounds.sh](../../tools/lan1rounds.sh)）：它只认这个脚本开始**之后**新到的字节里
`[    0.xxxxxx] Linux version` 这种带 uptime 的真 banner（中继的 `=== >>> autoboot` 标记不能用，理由见 docs/92 §96.59），
抓到就等 `POST_BOOT=90` s（§7.9：这板的可用窗实测从 boot+90 s 起），再把 `acceptlan1.ps1 -PingCount 25` + `lan1sweep-ssh.sh` + `attempt/758d` 的见证一起落进
`staging/ctl/lan1rounds.log` / `lan1rounds-boot<N>.txt`，然后等下一个边沿。对板子只读：不写 flash、不进 `sercmd.txt`、不发 `reboot`。
⇒ 无人值守整条链就是三条命令：`permit-waiver.sh` → `ARM=1 ubflash.sh 287` → `lan1rounds.sh 2`，没有一条需要人在场看时钟；
`serialkey.sh` 是挂在旁边的**条件步**，只有第 1 轮的 `acceptlan1.ps1` 报 rc=2 才轮到它（§7.12 12:5x 那张表说明为什么今天不需要预先跑）。
**这条探测已经排练过（10:56 实测，`DRY=1`）**：脚本 10:55:28 起监控 offset 131 084 933，**10:56:11 抓到 `[    0.000000] Linux version 6.18.38+`**，
紧挨中继自己的 `10:56:08 the kernel is up` 标记（差 3 s，与 §7.11 预测的 10:56:0x 边沿一致）；同一轮见证是
**`attempt=0 autoneg=0 codeword=只有 758d=0x0010`** —— 这正是「板上还是 pre-#287」应有的负控形态（docs/92 §96.58 的死态零点）。
⇒ 采样与见证提取这两件事已在真边沿上证明可用；#287 上场后同一命令要看到的差别是**明确的**：`attempt 1/3 → 2/3 → 3/3`（[1.6 s, ≈8 s, ≈23 s]）与 `758d` 的 bit2 翻起来。
**两趟见证的版本也在真边沿上排过（12:00 读排练日志）**：11:57:41 抓到 banner ⇒ 11:59:12 `witness_pass boot+90s`、12:00:29 `boot+165s`，
两次都是 `attempt=0 autoneg=0 codeword_values=758d=0x0010`、`pcrxwatch max rx_delta=0`（= 当前 flashed 镜像的死态），节奏本身没有落空。

**#287 上板前的判据读法不变**（§7.9 相位 B/C、docs/92 §96.54 与兄弟会话预登记的三种失败形态）：
`attempt N/3` 的时间线按 **[1.6 s, ≈8 s, ≈23 s]** 读；`758d` 的码字位（bit2）从 `0x0010` 变起来才算 witness 扳动；
**一次都不打 ≠ 试了没用**，那是路径没进去。
**结果必须在断电之前落盘** —— 断电 30 s 里什么都做不了，而 `staging/ctl/*.log` 是唯一的记录介质。

### 7.12 G4 的「ssh 可登录」这一支：钥匙这件事**已经在字节上结掉**（11:0x 那句「必然 Permission denied」被本节开头的表作废；docs/92 §96.70）

**（12:5x：本节的前提被字节证据作废 —— 板上那份 root 已经信这台 PC 的钥匙）**
上面那五步取证讲的是 **release 里烤进去的那把 `sk-d840n-flash-operator`**，而「今天的板子必然 `Permission denied`」这句
**没有验过板子上真正在用的 root**。现在验了，全部离线：

而这正是本节原本那条判据的读法，只是**触发条件现在有了字节依据，而不是每次预先占一个 20.5 min 的边沿**。
⚠ **诚实边界**：这份 dump 的时间戳是 10-20 20:45，此后 mainline 往同一块 jffs2 写过东西（只是没人擦 root）⇒「那把钥匙现在还在」是**推断**，
**G4 第 1 轮的那次 ssh 就是它的判决**；判决若是 `Permission denied`，跑一次 `serialkey.sh` 就是本节原方案的正当回归，不算新问题。

**结论先说**：#287 那次启动里 LAN1 就算完全通了，`ssh root@192.168.9.1` 也会 `Permission denied` —— 板子信的钥匙不在这台电脑上，
而我们的钥匙在 10-30 那次擦 root 时被一起擦掉了。不补这一步，一轮成功的 G4 会被记成失败。

1. CI 烤进镜像的是**另一把**：`overlays/target/linux/zte/zx279133/base-files/etc/dropbear/authorized_keys`

2. 本机 `~/.ssh` 里四把公钥逐个数指纹：`491797264`=`XI0Z8/VI…`、`Acer_8745h`=`Mh1SVMrr…`、`aliyun_8_137_101_164`=`kVlW9Gep…`、

   同一家族的事 doc 07 在 10-14 就记过（那把私钥的注释写着在 WSL 容器里，而这台机器 `wsl.exe` 直接回「未安装」）。
3. 我们手上这对是**有效**的：`ssh-keygen -yf ~/.ssh/id_onu` 与 `.pub` 逐字段相同 ⇒ 问题不是钥匙坏，是**板子不认**。

   和 `authorized_keys; chmod`，那是当年 `tools/serialkey.sh` 那一轮；而**最后一次 `DONE-root` 在偏移 127 543 314**
   （run 284，10-30 14:49）。`mtd write root` 是整片 jffs2 重写，`/root/.ssh` 跟着一起没了 ⇒ 现在板上只剩第 (1) 条那把。
   字节偏移在这里就是时间顺序：日志只追加，所以 5.75 M < 127.5 M 是硬证据，不需要墙上时钟。
5. 本轮 `stages=dtb kernel`**不写 root**（这是本案非目标），所以 #287 那次启动用的还是 284 的 root ⇒ 第 (4) 条继续成立。

**补法（一次性的，且不动 flash）**：第 1 轮启动后、测 ssh 之前，跑
`sh tools/serialkey.sh`（[tools/serialkey.sh:32](../../tools/serialkey.sh) 默认 `KEY=~/.ssh/id_onu`，装的就是第 (3) 条那对；
它把 `PUB` 写进 **`/root/.ssh/authorized_keys`** —— dropbear 的 strings 只会拼 `"$HOME/.ssh"` + `authorized_keys`，
所以这是确定被读的那条路径；`/etc/dropbear/authorized_keys` 会不会也被读，仍然**留给那次 ssh 自己回答**）。
它写 `sercmd.txt` 走同一套 interlock，所以只能排在**两轮之间**、不能和 `ubflash` 并行。

**判据因此精确化（不改目标的强度，只是把 provisioning 和稳态分开）**：
- 第 1 轮 = 冷启动 → `ping` 4/4 → `serialkey.sh` → `ssh` 登录成功；
- 第 2 轮 = 冷启动 → `ping` 4/4 → `ssh` 登录成功，**全程不碰串口**。
⇒ 「不再需要串口」验收的是**稳态可用性**（第 2 轮）；首次钥匙注入是一次 provisioning，与设备出厂后第一次装钥匙同类。
把它写在判据里而不是偷偷省略，是为了不让一次 `Permission denied` 冒充成「LAN1 又坏了」。

**被否掉的替代方案**（记下来免得下次再算一遍）：改 overlay 里 baked 的那把钥匙 = 要推 = 触发一个新 run = 整套 kit 重新取血缘；
而且真正生效要**写 root**，与 §0 非目标直接冲突。

**#287 不需要任何 env/bootargs 配合（11:4x 读源码清掉的一条怀疑，docs/92 §96.65）**：自愈的门是
[zx279133-switch.c:940-944](../../kernel-overlays/drivers/net/ethernet/zte/zx279133-switch.c) 的时间闸（15 s 一跳），
**里面没有 phylink/carrier/link 判断，也不被任何 DT 属性或模块参数门控**（文件里唯一的 `module_param_named` 是早有的 `wan_type`），
`lane_work` 每轮自我续期、只在设备清理时才取消 ⇒ 写进 dtb+kernel 两段就足够，§0「不动 U-Boot 环境」这条完全守住。
同时也解释了为什么 `lan5` 是 `fixed/2500base-x` 却仍然轮得到自愈 —— 它走的不是 phylink 的链路事件。
**取样时刻跟着改了两处**（都是会把成功读成失败的）：`lan1rounds.sh` 的 `POST_BOOT` 由 45 s 改成 **90 s**（§7.9 实测可用窗从 boot+90 s 起），
并且每轮做**两次见证**（boot+90 s 与 boot+165 s）—— 上限 3 次 = bring-up + 两次自愈，一次自愈里还要等 8 s 谈成 + 2 s 载码，
所以 `attempt 3/3` 可能落在 boot+45~55 s，单次见证会只数到 `2/3` 就把这轮定成「试了没用」。

**仪器侧同一轮补的口子**：`tools/lan1sweep-ssh.sh` 的执行体对**一台真的有 sshd 的机器**跑通了正控 ——
`lan1sweep-ssh: ssh rc=0, blocks completed 26 of 26, tag echo=1`、exit 0（`HOST=/KEY=` 指过去跑的；
扫里所有写动作的目标只有 `$D=/sys/kernel/debug/zx279133-9132`，所以在别的机器上跑不会写坏东西）；
负控（主机不可达）先前是 exit 3 / `ssh rc=255`。
⇒ 仪器本身能通也能失败，所以第 (3) 条那种认证失败**可以归因成板子的认证事实**，而不是「工具坏了」。

**判据的退出码就是判据（12:0x–12:1x，docs/92 §96.66）**：`tools/acceptlan1.ps1` 原来没有任何 `exit`，
所以「打印 FAILED」与「返回 0」同时成立（11:54:01 的正控制抓到），而 `lan1rounds.sh` 正是用返回码来数轮次。
现在返回码与文本同源：`0` = ping 够 **且** ssh 真登录（`G4-LOGIN-OK` 标记回显）= `VERDICT: PASS`；
`2` = ping 够但登录不进 = `VERDICT: PARTIAL`（就是本节这把钥匙，**不是** LAN1 死）；`1` = ping 本身不够 = `VERDICT: FAIL`。
`lan1rounds.sh` 只把 `rc=0` 的轮次记进 `G4PASS`，末行按 `G4 PASS / G4 NOT met - N of M` 直接给结论，
所以「连续两轮」这句判据不再需要人回头读日志。同轮堵掉的第二个口子更凶：远程串原本以 `dmesg | grep "lane:" | tail -1` 收尾，
一次**成功**登录若没有 `lane:` 行就退 1 ⇒ 判成登录失败 ⇒ **G4 第二条判据可能永远无法成立**；现在末尾钉一条 `echo G4-LOGIN-OK`，
退出码才真的等于「认证过了并跑到了最后一行」。
**死态基线（12:16:23，当前 flashed 镜像，非 #287）**：`arp: 192.168.9.1 state=Incomplete`、`ping: 0/2 replies - THE LINK DID NOT ANSWER`、
`tcp/22: CLOSED`、`rc=1` —— 判据在计划点名的那个失败特征（ARP `Incomplete`）上明确不通过。
**还缺的那一面明说**：`rc=0` 这条分支要等 G4 第 1 轮（先跑一次 `tools/serialkey.sh`）才会第一次被走通；在那之前不说「判据两面都验过」。

**`serialkey.sh` 也按同一把尺子补过了（12:3x，docs/92 §96.67）**：它原来 ssh 失败只打印、仍然返回 0，
和上面那条是同一个病。现在它的判据进退出码——
`0` = ssh 退 0 **且**回显 `WRITE-OK`（根真的写进去了，装的 key 才活得过一次切电：内核命令行是 `root=… ro` + `CONFIG_CMDLINE_FORCE=y`）；
`1` = 控制台没醒（`no shell on serial`）/ ssh 不登录 / 登录了但根写不进。
并且补了三样管路性的东西：仓库根 `cd` 锚点（原来从别处调用会把发送错误伪装成「板子没 shell」）、

## 8. M5 — 2.5G（明确推迟，不进 M1–M4 的验收）

M1–M4 建立的是 1000BASE-X 档。要到 2500BASE-X：`0x7580` 低 6 位需要 `0x16`（今天两次翻的是 `0x02`），PC 侧网卡也要支持并被迫到 2.5G。

已知但**未验证**的线索：devad `0x1e` 的 `0x6f10/0x6f11` 在两态一字不差（`0x084a/0x0021`），所以厂商 realtek 驱动 `rtl822x_set_serdes_option_mode()` 里那组 gen2 magic（`0x6f10=0xd455`、`0x6f11=0x8020`）**不是档位答案**——这条假设已在花钱之前被实测否掉（判决 AM）。`tools/lan1magic.sh` 因此不跑。
