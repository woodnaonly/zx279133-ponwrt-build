## 0. 目标、范围、非目标

**目标**：让面板上那只标着 LAN1 的 RJ45 在**冷启动 + mainline 6.18.38 + ImmortalWrt** 下自动可用——灯亮、链路 up、PC 能经它拿到板子的网络，**不依赖串口、不依赖人工干预**。

这条目标是**可用性目标，不是带宽目标**。今天被证明能跑通的是 **1000BASE-X 档**（loader 配好的那次启动，PHY 侧 `0x7580` 低 6 位 = `0x02`，`ping 192.168.9.1` 4/4）。**2.5G 是 M5 之后的独立目标**，不要把它写进 M1–M4 的验收，否则“能用”会被“没到 2500”误判成失败。

**为什么先做它**：板子上只有 LAN1 插了 PC。它不通，就等于板子彻底没有网络通道，所有后续工作（9132 转发、PON）都只能靠串口做，一轮只有 20 分钟。

**非目标**：
- **本轮不做 9132 硬件转发**。原请求（LAN↔LAN 不上 CPU）挂起，不是取消，见 §9。它对 LAN1 可用没有任何帮助，而且它的判据需要 LAN1 通才能测。
- 不动 `root` 分区、不做 zrec 恢复、不改 bootargs 之外的 U-Boot env。
- 不在本机编译。CI 是唯一编译通道，push 即触发构建。
- 不把 `eth0` 绑到 XMAC1 之外再猜一次拓扑；`0x140000`（XMAC0）承载 LAN1 已由计数器证明（docs/92 §96.47 的 A→B→A 字节对照）。

- 一次串口往返 ≈ 1.2 s/命令；一个窗口能做的写入试验个位数。

**活着的那次启动（20:54 boot，loader 跑过 net bring-up）**

**死的状态（mainline 自己配的冷启动，163 次采样）**

**差分已完成的部分（PHY 侧 17 个字 + 近端 7 个 xmac0 字 + 4 个 nppt 字）**
- `devad 0x1e` 的 `75f3 / 697a / 6a04 / 6f10 / 6f11`：**两态完全相同**（0x0002 / 0x0000 / 0x0403 / 0x084a / 0x0021）。
- `7580 7581 7587 7588 7589 758b`、`devad 7:00/01`、`devad 1:00`、`devad 0:00/01`：**两态完全相同**（除 `7580`）。
- `xmac0` 七个字（tx/rx/frame/mode/duplex/misc/send）：**两态完全相同**；`mode` 在 1650 次采样里恒为 0，§96.46 的 `MODE_CFG` 假设已因此作废。
- 只有三处不同：**远端 `0x758d` 0x0010 → 0x801e**、**近端 `nppt 84` 0 → 1**、**近端 `nppt 90` 0x280b → 0x2c03**。

⇒ 结论（判决 AM）：**这不是“少写了哪个寄存器”，是“少了一个状态迁移”。**

**已实测到的那个迁移**：`m45w 5 0x7 0x00 0x3200`（devad 7 reg 0 现值 0x3000，置 bit 9 = restart AN）把 `0x7580` 从 `0x9412` 拉到 `0x9402`，**重复两次成立**。driver 现在从不 restart AN，所以 PHY 从不重新锁存档位。

**SoC 侧（Uni SerDes）—— 本轮最后一个未收口的差分**
- **地址纠正**：Uni SerDes 的基址是 **`0x16100000`**（`zx279133.dtsi:449-451` `phy@16100000`；`zx279133-np.c:1203-1205` 的白名单把 `0x16000000`/`0x16010000` 标为 **PON SerDes / PON SerDes PLL**）。此前一轮抓的 84 个字抓的是 PON 侧，那份文件已改名 `staging/ctl/ponserdes-working.clean` 保留，但**它不是 LAN1 的证据**。
- 21:06 在活的启动里补抓了正确块的 73 个字：`staging/ctl/lan1-uni-working.clean`。
  `python staging/ctl/uni_profile_diff.py staging/ctl/lan1-uni-working.clean` →
  **`zx279133_uni_1g_profile`：0/49 word(s) differ**，`mode` 字（`0x16100054`）= `0x00000101`。
  即：活的那次启动，Uni SerDes 就是驱动里那份 base-X image 本身。
- 死态的对应抓取由 `tools/lan1waitdead.sh`（后台 b64hyy2tz）在下一次自动断电后写入 `staging/ctl/lan1-uni-dead.clean`。

**这条差分的两种结果都已经值得，写清楚以免下轮误读**：
- 若死态也是 0/49 ⇒ SoC 侧 image 也被排除，“loader 切档 mainline 没切”这条假设**作废**，全部注意力收敛到 AN restart / SerDes 重新初始化序列这一个动作上（M2）。

**⇒ 2026-10-30 21:13 实测，落在第一种分支，而且比预期更彻底**（docs/92 §96.49.2）：死态也是 **0/49**，两态的 49 字 image 完全相同（mode 字都是 `0x101`）；差异全在 image **之外**的 13 个模拟前端/CDR **结果**字上（`0x161000e8` 死=0 / 活=`0x78b2b41c` 这种形状）。

**⇒ 2026-10-30 21:16 M2 的第一个结果**（docs/92 §96.49.4/5）：`socw 0x16100054` 抠 enable bit 再放回 + AN restart，**第一次在 mainline 冷启动里把 `758d`/`7580`/`nppt 84`/`nppt 90` 四个 witness 全部扳到活态值**——但 `pcrxwatch` 的 `rx_delta=0`、板 `eth0` 的 `RX bytes` 恒 0、`TX` 持续涨 ⇒ **板子的 TX 计数是软件计数，帧没上线**。归因因此改成**编排顺序**：datapath 是在 lane 还死的时候 arm 的，lane 复活不会让它重做（`ip link set eth0 down/up` 实测不重做）。

**已完成（docs/92 §96.49）**：
- ~~1. AN restart~~ —— 单独做**不够**（第三次复现）：`7580` 翻到 `0x9402`、`an` 到 `0x002d`，但 `758d` 仍 `0x0010`、`nppt 84` 仍 0。
- ~~2. Uni SerDes enable-bit toggle + AN restart~~ —— **witness 全对**（`758d=0x801e`、`nppt 84=1`、`nppt 90=0x2c03`），**流量仍为零**：`pcrxwatch rx_delta=0`、板 `eth0 RX=0 / TX` 持续涨。⇒ 不是寄存器、也不是单个迁移。
- ~~3. `ip link set eth0 down/up`~~ —— 不重做 datapath，RX 仍 0。

**剩下的、按优先级排队的动作**：

1. ~~**rebind 实验**~~ —— **作废**（docs/92 §96.49.10）：`zx279133-eth` 的 remove 路径本身坏，
   `echo 19000000.ethernet > …/unbind` 在 `unregister_netdevice_many_notify+0xa40` WARN
   （`x13` = ASCII `lan-cpu0`），并把做 unbind 的那个 `ash` 一起拖死，之后两条命令没有回音。
   驱动 built-in，`rmmod` 不可用；而把 9132 端口属性字重写一遍同样的值是**无信息量**的
   —— 那些字本来就不随 lane 状态变。
2. ~~**"近端从未自适应"这条解释**~~ —— **关闭**（§96.49.9）：kick 之后那 13 个自适应字也翻到活态值
   （`0x161000e8` 从 `0x00000000` → `0x46cea835`，`cc/d0/d8/dc/e4` 与活态逐字相同）。
   近端确实收到信号并做了均衡，帧还是不过。
3. ~~**顺序假设只剩一种能证伪它的实验：把它写进启动期**~~ —— **已执行**（2026-10-30 21:57，commit `f5d573e`，已 push）。也就是直接进 M3 ——
   `outerphy_serdes_set()` 里加 AN restart，`phy-zx279133-uni-serdes.c` 的 inherit 分支加 enable-bit pulse。
   两者的天然顺序（`switch.c:3207` 早于 `:3231`）正好等于 21:16 实测有效的「先 AN restart、后 pulse enable」。
   **这条改道的理由要写清楚**：控制台上不存在干净地重跑 bring-up 的杠杆（第 1 条），
   继续在窗口里做运行期写只是在重复已经证过的 (a)；M2 的 (b) 判据由启动期补丁来回答。
4. **XPCS0 侧**（保留，但优先级降到补丁之后）：`xpcsw` 写 lane 1 的 `0x1f` 四个字
   （`0x2140 / 0x0020 / 0x2000 / 0x0000`）。**XMAC0 的 soft reset 不做**——它和 PCS 共享 reset 字，
   实测会把 `0x2c03` 打成 `0x280b` 且写回四字也救不回来（docs/92 §96.47 / `switch.c:3467-3494`）。

**判据（M2 的硬判据，两条都要）**：在**一次 mainline 自己配起来的冷启动**里，
(a) `758d=0x801e`、`nppt 84=1`、`nppt 90=0x2c03`；**并且**
(b) `pcrxwatch` 的 `rx_delta > 0` 且 `ping 192.168.9.1` 4/4。
2026-10-30 已经单独拿到过 (a)，**(a) 单独成立不算通过**。
**回退**：全部是运行期写，断电即回到原状态；不做 flash 写入。

## 8. M5 — 2.5G（明确推迟，不进 M1–M4 的验收）

M1–M4 建立的是 1000BASE-X 档。要到 2500BASE-X：`0x7580` 低 6 位需要 `0x16`（今天两次翻的是 `0x02`），PC 侧网卡也要支持并被迫到 2.5G。

已知但**未验证**的线索：devad `0x1e` 的 `0x6f10/0x6f11` 在两态一字不差（`0x084a/0x0021`），所以厂商 realtek 驱动 `rtl822x_set_serdes_option_mode()` 里那组 gen2 magic（`0x6f10=0xd455`、`0x6f11=0x8020`）**不是档位答案**——这条假设已在花钱之前被实测否掉（判决 AM）。`tools/lan1magic.sh` 因此不跑。

## 9. 挂起项（不是取消）

**9132 硬件转发（最初的请求）**：`zx279133-switch.c:2556` `port_bridge_join` 不设 `*tx_fwd_offload`、`:3002-3016` 的 `dsa_switch_ops` 没有 `port_fdb_add/del`。但原截图的因果链需要修正两点：
1. `tx_fwd_offload` 管的是 **CPU 发出的帧**，不是 UNI↔UNI；
2. 驱动已经在写厂商的 SA-learn / DA-lookup 位（`zx279133-np.c:2929-2937`、`:3356-3425`），docs/30 §4 记录过厂商 MAC 表里确实有一条学习项。
真正的门槛更可能是**flood group 每 group 只有一个目的口**（`zx279133-np.c:3315-3348` 把所有 group 指向 CPU 15）加上 **trap 覆盖 forward**；而**已知单播的 UNI↔UNI 从来没有被干净地测过**。测它需要 LAN1 通 + 至少两只口插线——这就是它排在 M4 之后的原因。

其他挂起：`tools/relayctl.ps1` 的进程匹配加 `pwsh.exe`（现在会误报“没有继电器”，从而导致有人去起第二个、然后撞上 `COM3 access denied`）。
**已修**（2026-10-30 21:56）：`RelayProcs` 的 Filter 改成 `Name='powershell.exe' OR Name='pwsh.exe'`。
顺带核对了一条事实：此刻持有 relay 的其实是 `powershell.exe`（PID 45360），所以 §1 那句“COM3 由已经在跑的 pwsh.exe 持有”
是当时的情形、现在不是——要修的从来是**那个假阴性**，不是哪一次的具体进程名。
