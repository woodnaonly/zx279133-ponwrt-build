# SK-D840N 面板 LED：原厂逆向与定点诊断（2026-11-03）

全灯常亮测试后，机主报告“2.5G/LAN1 和 USB 没有亮”。当时 10 个 LED 类设备都读回 `trigger=default-on`、`brightness=1`；LAN1 的 GPIO4_2 和 USB 的 GPIO1_5 均报告输出低电平。软件状态不能代替实物观察。后续单独操作已得到机主确认：PHY 工厂强制值能点亮面板 LAN1（§8.4），GPIO1_5 的标准 LED 接口能点亮 USB（§8.5）。仅翻转 PHY `d044` 位 0 也已在当前 1000 Mbps 链路下点亮面板 LAN1（§9.7）。机主确认本板 RJ45 插口没有灯，不需要面板与插口灯的独立性验收（§9.5）。LAN1 稳定开关字段、自动行为及 USB 完整自动行为仍待验证。

## 2. 原厂选择哪组 LED 配置

原厂设备树有 `leds`、`leds_2`、`leds_5`，USB/FXS 接线随组变化。原厂内核运行态备份 `../backups/last-good-419-20261013/state.txt:330–332` 明确记录：

```text
leds DTS probe by vid, successed
zx-leds-gpio soc:leds_5: 4 led has mux ctrl
zx-leds-gpio soc:leds_5: alloc devid 101711872
```

`../staging/ctl/vendor-dmesg-20261023.txt:316–317` 与 `boot419-window.txt:387–388` 也指向 `soc:leds_5`。`zx_led_probe()`（VA `0xffffff800837cd10`，file `0x2fcd10`）读取 `vid_list/sky_valied_vid`，与 `g_sky_hard_vid` 匹配后才注册这一组。

活动组在 [原厂 DTS](../decompiled/sk-d840n-stock.dts) 中声明：

| 原厂名称 | led-id | GPIO | 极性 | 本轮证据边界 |
|---|---|---|---|---|
| `led_usb1` | `0x34` | GPIO1_5 | 低有效 | 当前定义与原厂活动组一致；后续单灯常亮已确认，见 §8.5 |
| `led_phone1` | `0x51` | GPIO2_3 | 低有效 | 保留现有 FXS 控制；本轮未逐灯确认名称对应 |
| `led_lan0` | `0x00` | GPIO4_2 | 低有效 | 原厂节点如此声明，尚不能等同于面板 2.5G/LAN1 |
| `led_lan1`–`led_lan3` | `0x01`–`0x03` | GPIO4_3–GPIO4_5 | 低有效 | LAN2–4 的现有 GPIO 控制不改 |

GPIO phandle `0x50` 是 `gpio@10d10040`，`0x15` 是 `gpio@10d10080`。不能从非活动配置组复制 USB 引脚，也不能把原厂预留的 WPS、WLAN 或 USB2 名称当作板上实际安装的灯。

## 3. GPIO、pad 与复用值

原厂 `zx_gpio_request_enable()` 选择 GPIO 复用，`zx_pinmux_config()` 对对应复用字段做读改写；普通 GPIO 请求路径未发现额外 pad 供电、拉阻或驱动强度初始化。GPIO 的 DIR `+0x00`、DATA `+0x14`、SET `+0x18`、CLEAR `+0x1c` 语义与上游实现一致。

| 当前 LED 路径 | SoC pad | 复用寄存器与字段 | GPIO 复用值 |
|---|---|---|---|
| GPIO1_5（USB） | pin 21 / `p1-6` | `0x10e20004[17:15]`，mask `0x00038000` | `3` |
| GPIO4_2（LAN1 候选） | pin 62 / `p4-6` | `0x10e20010[8]`，mask `0x00000100` | `1` |
| GPIO4_3–GPIO4_5（LAN2–4） | pin 63–65 / `p4-7`–`p4-9` | `0x10e20010[11:9]` | 各字段 `1` |

这些映射与主线 pinctrl 驱动一致。因此，仅凭主线缺少其他 pinconf 能力，不能判定它是两灯未亮的原因。debugfs 的 GPIO 所有者也不保证硬件复用寄存器在稍后仍保持该值。

板上没有 `devmem`；已有 `/dev/mem` 定点读取返回 `Bad address`，没有得到这些寄存器的有效值。本轮没有扩大地址范围、绕过读取限制或安装新接口。工具将实际 mux 标为 `UNVERIFIED`，不把 debugfs 所有权代作寄存器读回。以后取得实际字段值才能与上表比较；即使值相符，也不能单独证明面板接线。

## 4. 外置 PHY 有另一条 LED 控制路径

`rlt8226b.ko` 的 `r8226b_led_enable()` 位于 `.text+0x551c`，file `0x555c`。它访问 MDIO1 地址 5 的 MMD `0x1f`、寄存器 `0xd044`：

| 厂商调用参数 | 原厂实现 |
|---|---|
| `0` | 读改写，清除 `[6:4]`，保留其余位 |
| 普通非零参数（如 `1`） | 读改写，置位 `[6:4]`，保留其余位 |
| `10` | 整个 16 位寄存器写 `0x0000` |
| `11` | 整个 16 位寄存器写 `0x00ff` |

`init_module` 注册 `r8226b_led_on_off_callbk`。原厂内核的 `zx_led_factory_set_all()`（VA `0xffffff800837c764`，file `0x2fc764`）在 VA `0xffffff800837c810`–`0xffffff800837c820` 的分支给状态加 10 后调用回调；普通 `zx_led_set_all()`（VA `0xffffff800837c8cc`）使用 `0/1`。这说明厂商有普通使能和工厂强制两种语义，不能混用。

`sky_outerphy_led_act()`（VA `0xffffff800837d86c`，file `0x2fd86c`）与上述回调提供了外置 PHY 控灯的真实软件入口。反汇编本身不能证明寄存器的全部输出就是单独的面板 LAN1；后续 §8.4 的机主观察已确认 `0x00ff` 能点亮面板 LAN1，但未排除同时影响其他 PHY LED 输出。`0x0000/0x00ff` 是整字强制值，不能作为普通 GPIO 常亮修复写入启动脚本。

原厂的四路 LAN GPIO也没有被排除：`zx_led_probe()` 会先选择 LAN 专用复用并释放 GPIO 描述符；`zx_led_set()` 手动亮度时重新申请 GPIO。由“原厂 debugfs 没占 GPIO”推断“只能由 LED 引擎控制”，证据不足。

## 5. USB 插拔模块只调用已有 LED

原厂 `usb_led.ko` 的完整 `.text` 与 `.init.text` 反汇编未发现 GPIO、pinctrl、电源或 MMIO 访问。`storage_led_action1` 在 `.text+0xc4` 停止软件闪烁，`+0xd0` 调用 `led_set_brightness(led,1)`；拔出分支 `+0x11c` 设置 0。`storage_led_action2` 使用相同的 LED API。

`init_module`（file `0x334`）先查 LED id `0x35`，再查 `0x34`，为单灯或双灯机型注册 USB 事件回调。`get_led_data_from_id()`（VA `0xffffff800837e6c8`，file `0x2fe6c8`）只按 id 查找 LED，不会把 USB1 的 `0x34` 改成另一只灯。

`zx_led_set_brightness()`（VA `0xffffff800837c354`，file `0x2fc354`）仅在 `zxic_isNotGpio == 1` 时附加外部回调。运行态属性清单 `../staging/ctl/vendor-dtb3.txt:342–345` 中，活动 USB1 只有 `default-state/name/gpios/led-id`，没有此属性或 `pmx`。普通亮度最终在 `zx_led_set()` 的 VA `0xffffff800837d848` 调用 `gpiod_direction_output(desc, brightness != 0)`。

早期 USB 强制 `default-on` 后未亮的观察，不能归因于缺少原厂 `usb_led.ko` 或 `usbport` 尚未检测到设备。后续单独操作已确认 GPIO1_5 能点亮 USB，见 §8.5。保留标准 `usbport`、USB1 的 sysfs 名称和 GPIO1_5；不新增厂商模块依赖，不交换 USB/FXS 引脚。

## 6. 定点诊断工具的边界

工具为 [tools/diagnose-sk-leds.py](../tools/diagnose-sk-leds.py)。默认只读：采集版本、板型、LED 状态、GPIO/复用信息及指定 PHY LED 寄存器；无法获取的项目记录为未采样，不以零值代替。检查对象固定在 SK-D840N 的已知路径，不扫描 GPIO 或未知 PHY 寄存器。

`--force-phy-led` 是显式写入入口，仅供机主现场观察时使用。写入目标限定为 MDIO1 地址 5、MMD `0x1f:0xd044`，先保存原始完整 16 位值，再做三轮“请求灭 2 秒、请求亮 2 秒”的 `0x0000/0x00ff` 强制测试。每阶段读回；正常结束或中断、异常时恢复原始整字并复核。原值读取失败、板型/目标不符或恢复无法确认时，停止并报告失败，不能继续尝试其他寄存器。现有 debugfs 命令实现使用 `mdiobus_c45_read/write()`，写操作之后另作真实读回，不以命令提交成功代替验证。

写入前，工具启动独立板端守护，忽略 SSH 断开产生的 HUP，关闭继承的标准流，并持有全局 `flock`。工厂及三轮候选位试验的期限固定为 30 秒；§9.7 的单候选位持续观察固定为 60 秒，从守护启动时计时。到期后先禁止后续阶段，再恢复原字。主机只有读回原字后才撤销守护；恢复失败不会写取消标记。持续观察模式将恢复交给独立守护，返回时明确报告恢复尚未完成，须另行核对恢复记录和新鲜读回。全局锁位于 root 私有目录，拒绝符号链接；旧会话迟到恢复必须重新取得全局锁，已有恢复记录只允许新鲜读回，不能重写旧值覆盖新会话。所有恢复都可能因设备或 MDIO 故障失败，届时报告未验证，不作成功保证。

实板的最小 BusyBox 不支持 `sleep 0.25`。该问题在 PHY 强制写入前发现并修正：每阶段使用两次 `sleep 1`，每秒核对载波和速率；守护也只使用整数秒。发生错误即停止后续阶段并尝试恢复。

该测试不修改 UCI、其他灯、SerDes、自协商或网络配置，不刷机、不重启。它可能影响外置 PHY 的全部 LED 输出；本板没有 RJ45 插口灯，机主只需观察面板 LAN1 及其他面板灯。没有人工观察就只能报告寄存器测试结果，不能报告 LAN1 已点亮。工具本身与恢复路径的离线测试，不代替这次实机观察。

USB 保留已知复用字段的只读取证项；实际 mux 读回仍缺少证据。§8.5 的实灯确认不等于补齐了 mux 寄存器采样，但已经证明标准 GPIO 路径能点亮这只灯。工具不改 GPIO1_5，不增加试写引脚、交换极性或 pad 初始化。

## 7. 验证与后续修改的条件

- 离线检查原厂素材 hash、VA/file 地址、GPIO 到 pad 映射及两种 PHY LED 语义；测试默认路径无写入，工厂/单候选极性试验只触及 `d044`，§9.8 的显式亮度候选试验另限通道 0 的两个 LED 事件字段。异常及中断均须核对完整原值恢复。
- DTS 去除注释后与修改前比较，确保本轮所有属性、网络端口映射和 sysfs 名称不变。历史记录仅追加带日期更正，不改写机主原话。
- LAN1：在机主能观察时执行受控 PHY 测试，分别记录面板 LAN1 及其他面板灯的响应，核对测试前后寄存器、链路状态和配置未改变。无响应就保留未定位结论，不将软件读回当通过。
- USB：§8.5 已确认 GPIO1_5 单灯常亮，不再把额外 mux 初始化列为修复前提。保留实际 mux 未采样的记录；后续需机主配合验证手动关闭、USB2/USB3 插拔和带设备启动。
- 只有面板控制路径证实后，才制定 DTS/驱动的功能修复；随后独立验证手动关闭、常亮、USB2/USB3 插拔及带设备启动。当前 LOS、LAN2–4 和 FXS 控制不随推测改动。

旧文档中“loader 时亮过，所以不需要 Linux 控灯”和“GPIO4_2 已证明就是面板 LAN1”的说法不再作为修复依据。`lan5` 只是现有 2.5G 网口 `lan1` 的历史名称；网口命名不会改变 `default-on` 的硬件控制路径。

## 9. 正式修复前的控制字段确认

### 9.1 新的上游字段依据及适用范围

Linux 提交 [`d3aae4d954f92a273388439ab015763e0cdea1e0`](https://github.com/torvalds/linux/commit/d3aae4d954f92a273388439ab015763e0cdea1e0)（`net: phy: realtek: Add support for PHY LEDs on RTL8221B`，2026-05-05）提供三通道 LED 实现，定义：

| 寄存器 | 上游定义 | 初次候选位试验允许的操作（后续授权见 §9.8） |
|---|---|---|
| `1f:d032 + 2 * index` | 单通道链路事件选择 | 只保留已有 `d032` 只读哨兵，不写入 |
| `1f:d040[index]` | 单通道活动闪烁 | 只读原字哨兵，不写入 |
| `1f:d044[index]`，`index=0..2` | `LED_POLAR(index)`，通道极性 | 可显式选择一次单候选位翻转，随后恢复原字 |

该提交把 LED 回调挂在 RTL8221B-VB/VM 驱动项，没有直接挂到板上 RTL8226B 对应驱动项。它只能作为候选字段依据，不能直接证明本板通道编号、有效电平或面板接线。

`rtl822xb_led_brightness_set()` 在更改 `d044` 极性前，还会清除选定通道的链路事件及活动闪烁。因而，仅翻转 `d044` 一个极性位不等同于常亮/关闭：它可能反相原有硬件事件。原厂 `[6:4]` 整组使能也不能直接当作已确认的单灯亮度字段。本轮不把这些其他 LED 寄存器加入写入范围。

### 9.3 单候选位诊断与停止条件

[诊断工具](../tools/diagnose-sk-leds.py) 默认仍为只读。显式选择 `--invert-phy-led-channel 0`（也接受 `1` 或 `2`）后，工具保存新鲜完整原字，启动独立 30 秒恢复守护，进行三轮“原状态 2 秒、仅翻转候选位 2 秒”，最后恢复完整原字并复核。每次写入仍只针对 PHY 5 的 `1f:d044`，完整读回必须匹配，其他位不得改变；链路、速率、UCI 和原有哨兵检查保持不变。

该模式使用 `BASELINE/INVERTED` 命名，不宣称 `OFF/ON`。候选位仅限上表的 `[2:0]`；它与工厂整字试验互斥，同一会话也禁止切换候选位或混入工厂命令。阶段写入前再次检查守护期限，超时、写入失败、读回不符或中断时走完整原字恢复流程。

截至本节记录时，本轮只运行了默认只读采集，尚未执行候选位硬件写入。需机主观察面板 LAN1 及其他面板灯，记录每个阶段的变化。即使单个位能反相面板，还必须确认可保持常亮/关闭及其与链路事件的关系，不能把一次反相观察当作完整开关语义。

此前曾把面板与 RJ45 插口灯独立控制列为前提，§9.5 的机主更正使这一条件不再适用。当前仍缺面板 LAN1 的稳定开关字段证据，因此尚未注册新的 LAN1 LED 后端、删除 GPIO4_2 节点或改动十路 GPIO 声明检查。确认面板控制字段后，再接入 `brightness_set_blocking` 并将描述移到现有交换机端口下；不创建第二个同名 LED，不绑定或复位 PHY。若需要写入本轮范围外的寄存器，须先说明证据和修改范围，再取得方向确认。
