# 92 · 2.5G 那个丝印口是交换机的口，不是 eth0 的口（2026-10-26 晚）

目标（owner 原话）：「板子插在智能开关上面 设定20分钟通电 ，20秒钟断电循环，要求你持续跟进 ，
网线插在lan1 2.5g 口 并调通」。这一篇记录今晚为 LAN1 取得的全部测量，以及它们把哪几条假设否掉了。
智能开关的节奏是 20 min 通电 / 20 s 断电，每一个 U-Boot 窗口都是这么来的。

标注约定：**量到的** = 有原始行；**推出的** = 由量到的推出来；**没定的** = 还缺哪一行。

**读前先知道：本篇标题和 §13 的那句结论，都被后面几节各自改了一次。**
（一）「把 2.5G 口声明成交换机的口」不是这条通路的开关——§11 运行期把 mem 5 配成一个真能用的口的完整
配方之后，PC 的 20 帧仍然一个都没到 CPU。**但 §11 否证的范围比它当时以为的小**：那轮实验做在
mainline 已经把自己那条 lane 重编过一遍之后（§15），所以它没说清「声明」在一个**通着的** lane 上到底行不行。
（二）§13 那句「没有任何计数证明 PC 的帧到达 XMAC0 的收方向」**用的两个计数都是发方向**（§15 量到的：
只有 PC 出声的那一段它们一个字都不动，而 `+0x2070` 是本仓库头文件自己命名为 `TX_FRAMES` 的字），
所以那条结论撤销，收方向的计数**至今没找到**，找它的工具是 `tools/ubmacfind.sh`。
（三）现在最硬的一条是正向的、也是今晚唯一一条从**通着的**开机里拿到的：丝印 LAN1 的 MAC 是
`nppt+0x19140000` 那一块，四个 SMAC 窗口和 mainline 的 eth0 唯一会碰的 `0x19180000` 窗口
在一条被证明通着的线上全程为 0（§14、§15）。剩下活着的嫌疑按价值排序在 §15 末尾与 HANDOFF。
（四）§20 说"mainline 与通流开机的差是四位"——§21 把它**加强成"这四位全是 mainline 自己改的"**：
它在两个开机里上电第一行读到的 `lane pre-serdes` 就已经等于通流的配方，是它自己把
`tx/rx/frame/misc` 改坏的，还**多改了第五位**（PCS vend2 `AN_CTRL 0x0005 → 0x0015`，bit4）。
（五）因此 `zx279133-switch.c` 里"引导程序把 XMAC0 留在 0、每个控制字都读 0x00000000、所以从来
没人配过它"那段注释，在**这根线、这块板**上是假的，它描述的是线不在 LAN1 时的状态（§21）。
同时撤销的还有 §20 末尾把 `tools/liningress.sh` 当判决仪表的安排：mainline 下 `nppt+0x20204/0x20210`
在所有窗口里都以 `0.32~0.35` 字每秒匀速增长，对 PC 的 40 帧和板子的 10 次 ping 都没有台阶，
`0x200b8` 恒 0 —— 它数的不是网线的帧，docs/65 §5 的形态没复现；换 `tools/ubingress.sh` 到**通着的**
U-Boot 里重做同一激励，才能定这批入口计数到底能不能当尺。
（六）§31 那张"`txp` 扫到原厂的 4 也没用"的表**整张撤销**：`txp` 写的是 `eth->lan_tx_port`，而
eth0 自己的帧在 `zx279133-netdev.c:382` 走的是另一支，取模块参数 `zx279133_tx_port`，那个值在刷进
flash 的 run 185 里**连符号都没有**（§32 grep 过 kallsyms）。于是"出口端口不是开关"对 eth0 只有
§3 那一个值（5）的有效读数。同时把 §27 的否证范围写清：它写对的是 XMAC0 的**控制字**，没动
**队列↔MAC 的绑定**，所以它否证不了 §32 末那条 A。**唯一还没被运行期量死的东西就是 A。**

## 4. 一次差点被我当成突破的假阳性，记下来

20:13 PC `ping -S 192.168.9.25 -n 6 192.168.9.1` 报「已接收 = 3」，20:14 `-n 10` 报「已接收 = 5」。
看着像 LAN1 通了。**它不是**：同一时刻 PC 的 IPv4 邻居表里
`192.168.9.1 → 00-00-00-00-00-00 / Incomplete`，也就是这台 PC 从来没解析到板子的 MAC，
因此它没有向板子发过单播 echo request，那 3/5 个「收到」是本机生成的差错回复。
判据要写成**两条**：收到回包 **且** 邻居表里有那块 MAC。只看 ping 的计数会把死口报成活口。

## 5. 否证掉的两条，别再走

## 7. 下一步（只有一条，因为它是剩下唯一能定死编号的读法）

`tools/ubxmac.sh`（已修，等 20:2x 的窗口）在 U-Boot 刚 ping 通之后读：
`spa_port_attr_op 0`（芯片自己的 port↔MEMID 表）、四个端口块、`0x19140000`/`0x19180000` 的
TX/RX 控制、`0x161000e4`（Uni SerDes 状态：今晚是 `0x01000706`，bit0 RX LOS = 0，**物理层认为自己有
rx data**）、以及刚用过的那条 TX 描述符。

要定死的问题是：**RTL8226 在 9132 的 SPA 里是几号口**。三条旁证都指向「它是交换机的一个口」——
原厂 `uni-phy` 数组第 5 项是 `0x05`、docs/13 的 `port=4 outerphy_mode=5,phy_RTL8226`、
docs/15 的「RTL8226 = switch 口 4 = 芯片口 5」——而我们的 DSA 节点只声明了 port@4..7（lan1..lan4）
加 port@8（CPU）。**如果它是一个交换机口，那 mainline 的缺陷不是 eth0 的端口号，而是这个口没有被声明**：
没有 port 节点 ⇒ 没有 PVID/转发 ⇒ 芯片不会把它和 CPU 通道互通，于是 Linux 下这个丝印口两头都是黑的，
而 U-Boot 拿它当 extend 口直接驱动，所以能用。

推论（还没做，等 §7 的表落定）：在 `&nppt`/switch 的 `ports` 里给它补一个用户口，按 docs/90 已验证的
transport-VID/PVID 方案同构处理，然后让它进 `br-lan`。真要这么做之前，面板命名要先问 owner：
`lan1` 这个标签在本 SKU 上没有丝印口（docs/90 §6），新增的这个口对应的丝印是 LAN1。

## 9. 新证据：两次开机在 MAC 窗口上是**不一样**的（今晚最关键的一行）

同一块板、同一个丝印口，U-Boot 的 ping 通了之后读（`tools/ubxmac.sh`，20:25 窗口）对 RAM kit 基线（20:48）：

| 窗口 | U-Boot（流是通的） | mainline RAM kit |
|---|---|---|
| `0x19040000` / `0x19080000` | `00ba2200 00003fff 80000001` | `00fa2203 00003fff 80000001` |
| `0x190c0000` / `0x19100000` | 同上 `00ba2200 …` | 同上 `00fa2203 …` |
| `0x190400e0` / `0x190800e0` | `00011000` | **`00011200`** |
| `0x190c00e0` / `0x191000e0` | `00011000` | `00011000` |
| `0x19140000`..`+0x0c` | **`60010000` ×4** | **`60010001` ×4** |
| `0x19180000`..`+0x0c` | **`00000000` ×4** | **`60010001` ×4** |
| `0x1900c0f0`（SMCT 指针） | `0xfc→0x65`（会倒退，是指针） | 基线 `0x4f`，扫到 port1 时 `0x7e` |
| `0x161000e4`（Uni SerDes 状态） | `0x01000706`（bit0 RX LOS = 0） | `0x01000706` 一样 |

三条读起来最有分量的：

1. **`0x19180000` 在 U-Boot 里是全 0，在 mainline 里被写成 `60010001`（bit0 使能）。**
   按 `zx279133.h:834` 的命名，`0x180000` 正是 XMAC1，而 `zx279133.h:28` 的默认端口 6 = XMAC1 ——
   mainline 把 U-Boot 从来不开的那个 MAC 开了，并把 eth0 的帧全送给它。
2. **`0x19140000`（XMAC0）在 U-Boot 是 `60010000`（bit0 = 0），mainline 是 `60010001`。**
   也就是说两份状态里唯一的 bit0 差别，方向是相反的：通流的那份**没**使能，不通的那份使能了两位。
   `zx279133-mac.c:31,413` 只用 `ZX279133_XMAC1_BASE`，所以这两个窗口的差值不是它写的 —— 谁写的还没定。
3. **四个 `+0x40000` 步进的块从 `00ba2200` 变成 `00fa2203`，两块 `+0xe0` 从 `0x11000` 变成 `0x11200`。**
   §5 那句「mainline 没人写它们」因此要撤回：Linux 侧确实改了它们。改它们的是谁，正在查
   （nppt 基址 +0x40000/0x80000/0xc0000/0x100000 这四个窗口）。

**下一轮要读的东西已经明确**：把 `0x19140000`、`0x19180000` 和四个块的写者找出来，然后判断
「eth0 该走的 MAC 窗口到底是哪一个」——现在所有证据都说 eth0 在驱动一条 U-Boot 根本不用、
而 RTL8226 也不在上面的 lane。

## 10. 20:54 量到的：帧**确实进了 SoC**，只是没到任何一条到 CPU 的队列

RAM kit（同一个 boot），先读 SOPC 计数器，然后从 PC 往线上打 12 个 ping（打不响也没关系，
ARP who-has 已经是真帧），再读一次：

```
                 BEFORE          AFTER(+12 ping)
0x19034100:  0x00650065   ->   0x00860086      +33
0x19034104:  0x00120012   ->   0x00120012      0
0x19034108:  0x000f000f   ->   0x000f000f      0    <- sopc_to_smac5
0x1903410c:  0x0003000f   ->   0x0003000f      0
0x19034130:  0x00080008   ->   0x00080008      0
0x19034134:  0x00070007   ->   0x00070007      0    <- sopc_req_smac5
```

同一个 boot 里 `ethtool -S eth0` 的收方向：**`rx_irq_count 0`、`rx_napi_polls 0`、
`rx_desc_not_ready 0`** —— 描述符环一次都没被弄就绪过。

把两件事放在一起，故障点被夹住了：

- PC 的帧进了芯片（`0x19034100` +33），
- 但**没有任何一条到 CPU 通道的 smac 计数动过**（`sopc_to_smac5` / `sopc_req_smac5` 都是 0 增量），
- 于是 CPU 侧的环、中断、NAPI 全空。

这就是「这个口在芯片里没有被接到 CPU 通道」的形状：帧进得来，转发不到 CPU。
和 §5/§8（出口端口字段两头都不是病因）、§9（mainline 打开了 U-Boot 从来不开的 `0x19180000`）一致。

**所以 #29 是剩下唯一的一条实现路径**：把 RTL8226 作为交换机的一个口声明出来，并按 docs/90 已验证的
transport-VID/PVID 方案接到 CPU 通道上。要做的第一件事实是芯片给它的是第几号口 —— U-Boot 的 CLI 读不到
（§7），就改用原厂二进制里已经解出来的两条：`uni-phy` 数组第 5 项 `0x05`、
docs/13 的 `port=4 outerphy_mode=5 phy_RTL8226`，配合 RX 描述符里那个源端口 5。

+0x2400/+0x2070）也一起读，因为原厂 CLI 把这个 PHY 报成 `port:0x4`，SMAC3 没有被排除。

**今晚第一条能变成补丁的机制**（从已有日志里挖出来的，不用新窗口）：mainline 自己 23:09 之后那次开机打的字——

```

lane pre-serdes: XMAC0 tx=0x60010000 rx=0x3e8000c6 frame=0x80000001 mode=0x00000000 duplex=0x00000100 misc=0x00002000

```

`pre-serdes` 就是「引导程序交下来的原状」（`switch.c` 在动它之前读的）。可 `zx279133-switch.c:2059` 的

⇒ **这个分支在本板上永远走不到**，于是每次开机都会走另一条：`xpcs_sgmii()` + `xpcs_bypass(true)` +

0x3800 这个掩码是从本仓库的 RTL8372N 驱动抄来的（:2104 的注释自己这么说），它是不是这颗芯片这条 lane

如果它也读 `0x2c03`，那 `link=down` 是 mainline 的**误读**，而这次误读正是它去覆盖引导程序配置的理由。

`0x19180000` 窗口在一条被证明通着的线上一个计数都没有。这同时否掉两样旧东西：
docs/18 §4 的「RGMII MAC + RTL8226 是另一个独立口（jack 4）」在本板上不成立，
而 U-Boot 打的 `port:0x4` 不是 SPA 口号（SPA 4 = SMAC3 = 丝印 LAN4，那块窗口今晚全程为 0），
它是原厂 outerphy 描述表里的序号——和 docs/13 的 `port=4 outerphy_mode=5 phy_RTL8226` 是同一张表。

**量到的第二件（方向）——这一条把 §13 的结论撤销了一半**：只有 PC 出声、板子静默的那一段，
`+0x142400` 和 `+0x142070` **都没动**（2→2），要等板子自己 ping 出去才 2→11。
而 `+0x2070` 是本仓库自己的头文件命名为 TX_FRAMES 的字。所以这两个字很可能**都是发方向**，
那么 §13 那句「现在没有任何一条计数证明 PC 的帧进了 9132 的 XMAC0」就不能当成已证的结论保留——
它更可能是在说「这两个字从来不是收计数」。收计数的字在哪一个偏移，今晚还不知道；
`tools/ubmacfind.sh`（23:49 窗口）就是为它写的：把 `+0x2000..+0x2180`、`+0x2400..+0x2480`、
`+0x2200..+0x2280` 整块 dump 三段，用**子网广播 ping**（不需要 ARP，所以板子可以一个字都不发）
当单向激励，谁的静默段涨了谁就是收。

**量到的第三件（PCS 判据）**：`nppt+0x90` 在一条**今天真的通着**的 lane 里三段都读 `0x2c03`
（bit11、bit12 缺），而 2026-10-21 docs/18:92 在同一个地址读到的是 `0x380b`（bit11,12,13 全置）。
`zx279133-switch.c:2059` 的「引导程序把链路留着了，继承它」要求 `(status & 0x3800) == 0x3800`，
:2104 的注释自己说这个掩码是从本仓库的 RTL8372N 驱动抄来的。⇒ **在今天这个状态下，mainline 每次开机都
走不到继承分支**，它做的是另一条：`xpcs_sgmii()` + `xpcs_bypass(true)` + `xmac_configure(do_reset=true)`
（:2068-2089）——也就是把引导程序已经调通的那条线重编一遍。0x380b 与 0x2c03 之间那一位差是什么
（对端换了？AN 没完成？10-21 那次线在别的口？）**没定**，这要等 run 189 的 `m45` 读 PHY 侧的
`1e.758b/758d` 才能判——正好是今晚排着的 #30。

**量到的第四件（一份 carrying boot 留下的完整配方）**：

```
tx=0x60010000  rx=0x3e8000c6  frame=0x80000001  mode=0x00000000  duplex=0x00000100  misc=0x00002000
SOPC mac0 ready(0x190342a4)=0   SOPC mac1 ready(0x190342a8)=0
Uni SerDes PLL(0x161000d0)=0xc880bb83   RX_STATUS(0x161000e4)=0x01000706
```

mainline 今晚的 `lane pre-serdes` 快照读到的六个字和这一组**逐字相同**（同一晚的串口日志），
所以「引导程序交下来的状态」Linux 是看得见的、也是照抄得对的；出事的是它抄完之后又改了一遍。
两处新差别记下来别丢：
(a) `switch.c:2047` 说「活板上 mac0 的 ready 读 0、**mac1 读 1**」——那是在 Linux 里读的；
在 U-Boot 里两个都读 0。
(b) PLL 字 U-Boot 读 `0xc880bb83`，mainline 的驱动打印 `0xc87fbb83`（中间字节 `80` vs `7f`）——**没定**，
`RX_STATUS` 两边一致（`0x01000706`，bit0 RX LOS = 0 ⇒ Linux 里 SerDes 也看得见光/信号）。

**否证掉的一条打算**：`md 0x1a000000`、`+0x104`、`+0x400` 都读 `00000000`。所以「去 XPCS0 的窗口
抄一份可用参考」做不到——那颗 PCS 是 C45 间接访问的（mainline 走 `mdiodev_c45()`，`mac.c:79-94`），
不是平映射；能当证据的只有 `nppt+0x90` 这个镜像字。

## 16. `phy sereds mode : 0x6` 是什么，以及为什么它不能和 mainline 的 `mode 0x1` 相减

23:29 那轮每次 ping 都打出 `test:cur 0 phy sereds mode : 0x6, last mode0 : 0x6, last mode1 : 0xc`。
这行很容易被骗——它会让人以为"所以 SoC 侧该配成 6，而 mainline 配的是 1/0x101"。**不是**：这五个数字
属于五个互不相干的命名空间，本地文件里都有出处（三条我逐字复核过，标 ✓）：

| 数字 | 它数的是什么 | 出处 |
|---|---|---|
| `0x6` | PHY 侧的链路模式**枚举**，= 1G 档 | ✓ `np_133.ko` 的 `outerphy_xmac_partner_check`（`.text+0x19ed8`，`staging/ctl/_np133_funcs.txt:276`）；枚举表在 ✓ `staging/k/drivers_net_phy_zx279051.c:479-481`「modes 2/5/6 都下 `mode_eth_1gbase_x_cfg`，modes 3/4 下 `mode_eth_2p5gbase_x_cfg`」⇒ **6 = 1G**，和本机 PC 网卡报 `1 Gbps` 一致；另见 ✓ `staging/src/cnjn-FIRST_PATH.md:53`「1 Gbit/s host interface … PHY SerDes mode 6」 |
| `7`（`uni_serdes_init(port,7)`） | SoC 侧 Uni SerDes 的 **profile 序号**（1gbase_x 那一档镜像） | docs/07:13498、13507-13509 |
| `2` | `OUTERPHY_XMAC_WORK_MODE_1000BASE_X`，XMAC 的工作模式 | `tools/smac6.sh:33-35` 引的原厂 help 串「`xmac_test xmac_work_mode_set [xmac_id] [work_mode]`」+ docs/07:13237 的 `speed set 2 in sgmii (xmac speed 3)` |
| `0x1` / `0x101` | **我们驱动自己的** `readl(serdes+0x54)` MODE_CTRL（BIT0 = enable），跟上面三行不同类 | `phy-zx279133-uni-serdes.c`（打印 `mode %#x already` 的那句） |
| `outerphy_desc_mode = <0x00 0x05 0x00>` | dts 里 PHY 的描述序号（`phy_RTL8226`），也不是链路模式 | `decompiled/sk-d840n-community-4.19.dts:1184` |

**由此**：`0x6` vs `0x1/0x101` 的"差"是假的，不能作为缺陷登记；`0x161000d0` 的 `c880bb83` vs `c87fbb83`
也只是同一字里一段没被任何文件解码过的只读状态带（两边 bit0 都 = 1，docs/07:14873 明说连 BIT(0)="PLL_LOCK"
都**没验证过**）。这一节的用处是把"mode 数字对不上"这条岔路堵掉。

**还剩下的一条真岔路**，而且 §15 的读数正好指到它：`0x6` = 1G ⇒ 这条 lane 走的是
**1000BASE-X/SGMII 且带 AN** 的档；而 mainline 从来**没有跑过原厂面向这颗 outerphy 的那套写**
（`1e.7581` BIT(4) 复位、`1e.7588`→`1e.7589 = 0x70d0/0x71d0` 的 AN/mode 选择、`1f.a436/a438` 的 DSP 补丁；
`zx279133-np.c:1308-1319` 自己就把这几条列成注释，代码里没有），generic realtek 驱动只在 probe 时**读**这颗 PHY。
判决还是 §15 末尾那句：run 189 的 `m45` 把 `1e.7588/7589/758b/758d` 读一遍，
和 `staging/ctl/ubattr-phy.txt` 里那条通流线留下的 `00CE / 035A / 0005 / 801E` 对——
不一致就 `m45w` 现场重放，一致就缺口在 XMAC0 的收使能（而收计数在哪一个字，23:53 排的那轮正在找）。

## 17. 00:02：run 189 真的 RAM 起来了，`m45` 十个字**全等**——PHY 侧那条嫌疑关门

`tftpboot 0x89000000 sk-d840n-initramfs-run189.itb`（12156484 B）在 00:02:10 交板成功，
内核 banner 之后 `tools/linuxphy.sh` 用 `m45` 把原厂那十个 CL45 字读了一遍。
左列是 22:08 那次**通流的 U-Boot**（`staging/ctl/ubattr-phy.txt`，同一次开机里

   所以"读得到"本身就证明了 mdio1/addr5 这条路在 Linux 里是通的。

## 18. 00:08 同一个 RAM boot 里 `xmacrole.sh`：那两块统计字的语义**还没被证明**，而且 eth0 的 TX 到不了 XMAC1

`tools/xmacrole.sh` 在 run 189 的 Linux 里读同样四个字，三段（空载 / `ping -I br-lan` 20 发 / `ping -I eth0` 20 发）：

| 字 | idle | bridge | eth0 |
|---|---|---|---|
| `nppt+0x142400` | `0x000021ea` | `0x00002218` | `0x00002242` |
| `nppt+0x142070` | `0x00002074` | `0x00002074` | `0x00002074` |
| `nppt+0x182400`（XMAC1） | `0` | `0` | `0` |
| `nppt+0x182070`（XMAC1） | `0` | `0` | `0` |

**这两件事必须分开看**：

- `0x142400` 在 mainline 里是**空载也在往上爬**（约 1/秒，40 秒 +46），而 22:0x/23:0x 那两轮在 U-Boot 里
  它是 2、3、11、13 这样的小数。⇒ 它不是一个纯"帧数"，至少不是只有帧才动。§14/§15 用它做的
  「口在 `0x19140000` 这块」那条**正向证据仍然成立**（同一台 boot 里 XMAC1 与四个 SMAC 的对应字全程 0、
  只有这块跟着 ping 动），但**它数的是什么**这件事从现在起是**没定的**，别再把它当 tx/rx frames 直接换算。
- XMAC1 的两个字在 mainline 里**恒为 0**，而 `eth0` 自己的 `tx_packets` 空载就上百（docs/92 §13 记过 170）。
  ⇒ **eth0 计入的发送，从来没有到达它自己编程的那块 MAC 窗口**。这是今晚新的一条正向缺陷，
  和 §14 的"eth0 在驱动一条 U-Boot 从不开的门"合起来看：两边都不动，说明问题不在"选错块"这一层，
  而在"到 MAC 的那一跳"。

## 19. 00:00 那轮"收计数在哪都找不到"作废：激励没被证明上过线

`ubmacfind` 的第一次运行（00:00:10 抢到 prompt、`is alive` 在内）把 `+0x2000..+0x2180`、
`+0x2200..+0x2280`、`+0x2400..+0x2480` 整块读了三段，结论打的是
`VERDICT NO-RX-COUNTER-IN-DUMP`。**这个结论不能留**，因为它的"只有 PC 出声"那一段用的是
`ping -n 20 192.168.9.255`，而 Windows 并不保证真的往子网广播发 ICMP——那一轮没有任何东西证明
那 40 帧上过线。仪表的错误和板子的答案长得一样，这就是本仓库已经写过的那类"只会打印通过的门"。

已改（00:10 武装的那轮开始生效）：

- 激励换成 **40 个 `SO_BROADCAST` UDP 数据报**（目的端口 9），由 python 自己打印交进驱动了多少字节；
  广播在栈里直接解析成 `ff:ff:ff:ff:ff:ff`，不需要 ARP，所以板子一个字都不用发，方向是单向的**由构造保证**；
  板子坐在 prompt 上也不会回任何东西。
- dump 范围从四个猜的块加宽到 `0x19140000 +0x40` 与 `0x19142000..0x19142600`（每块 `md <a> 0x100`，
  每条 md 的**所有行**都留，别再像 §9 那样只留最后一行）。
- 判决规则不变：一个字段只有在"只有 PC 出声"那一段涨、且涨得比静默背景快，才算这条线的证据
  （`tools/lanerate.sh` 立的规矩）。

若这一轮点名出某个偏移，`tools/linrx.sh` 就在同一晚的 flash Linux 里用 debugfs 的 `reg` 读**同一个字**
（`0x14xxxx` 全在 NPPT 窗口内，不需要出包），三段一样：空载 / 只有 PC 出声 / 板子自己发。
那时候才第一次有资格说"帧到不到 XMAC0 的接收端"。

## 20. 从已有日志里挖出来的第四条：XMAC0 的控制字与通流开机的差**不是两位，是四位**

不用新窗口——同一次串口的 boot 里，`zx279133-switch.c` 自己在 `lane pre-serdes`（引导程序交下来的原状）
和 `lane after`（它自己编完之后）各打了一行。把今晚 LAN1 那次和早先线在别处那次并排放：

| 字 | 通流的 U-Boot 交下来 | mainline 编完之后 | 差 |
|---|---|---|---|
| `0x140000` TX_CTRL | `0x60010000` | `0x60010001` | bit0 **多置** |
| `0x140010` RX_CTRL | `0x3e8000c6` | `0x3e8000c7` | bit0 **多置** |
| `0x140020` FRAME_CFG | **`0x80000001`** | `0x80000000` | bit0 **被清掉** |
| `0x143400` MISC_CFG | `0x00002000` | `0x00002200` | bit9 **多置** |
| `0x140280` MODE_CFG | `0x00000000` | `0x00000000` | 无（mainline 那句 `=2` 的写**没落上**，与 docs/92 §5 一致） |
| `0x140500` DUPLEX | `0x00000100` | `0x00000100` | 无 |

另一行更早的 boot（线不在 LAN1）留的是 `tx=rx=frame=mode=0`、`XPCS0 status=0x380b link=up`、
`xmac_link=0x0000`；今晚这条留的是 `tx=60010000 rx=3e8000c6 frame=80000001`、
`status=0x2c03 link=down`、`xmac_link=0x0001`。**⇒ 10-21 那个 `0x380b` 与今晚 `0x2c03` 的差，
是"对端是谁/在哪"造成的两种不同的通流状态，不是同一状态的前后**——`link=up` 那次和 `link=down` 这次
都各自是通着的开机的起手状态。所以 `switch.c:2059` 用 `0x3800` 当"可以继承"的判据，
最多只能覆盖其中一种，这条已经够登记为缺陷。

**最要紧的是 FRAME_CFG 的 bit0**：通流的开机里它是 **1**，mainline 按 `np_133.ko` 的常数
（`0x80000000`）把它写成 **0**。docs/65 §5 量的那个形态——138 帧交给 RED、136 帧因为
"交给它的长度是 0"被丢——正是一个**成帧**字该负责的东西，而不是 RX 使能。
`tools/xmacrx.sh` 因此从"只动两个使能位"改成**一次把四个字全部还原成通流开机交下来的值**
（tx `60010000` / rx `3e8000c6` / frame `80000001` / misc `2000`），先用一次实验判"整组还原能不能让收侧活"，
能活再一位一位二分；`RESTORE=1` 复原成 mainline 自己的写法，断电也复原。

判决仪表是 `tools/liningress.sh`（docs/65 的原厂入口计数），排在 00:20 那一轮 hunt 交回板子之后：
`liningress → xmacrx → liningress`，两次的差就是答案。

## 21. 00:25–00:34：`liningress → xmacrx → liningress` 跑完了，量到的是"第五条差"和"这把尺不灵"

两件事同时成立，所以这一节一半是成果、一半是把 §20 末尾那句"判决仪表"作废。

**先记账：两个工具的解析都是坏的，值是从原始行里重新提出来的。**

- `tools/liningress.sh` 的 `grab` 按字面匹配 `(nppt +$off)`，而 `zx279133-np.c` 打印偏移用的是
  `%06x` 补零——`0x20204` 在日志里长成 `+0x020204`。于是五个短偏移（`0x20204 0x20210 0x200b8
  0x200bc 0x28c4 0x28e4`）全落空，只有六位的 `0x280180 0x280240` 和 `0x140010 0x140000` 解析得到。
  同一个坑在 `tools/linrx.sh` 的 `word()` 里也有一份。**"空值"和"这个字不动"长得一模一样**，
  这正是本仓库反复登记的那类假阴性。两处已改成先 `printf '0x%06x'` 再匹配。
- `tools/xmacrx.sh` 的 `before=$(readone)` / `after=$(readone)` 忘了传参，`set -u` 下函数里的 `$1`

  写入到底有没有落地，由 `liningress#2` 自己的回读独立证明（见下表最后两列）：`regw` 之后
  `reg 0x140000` 连着四次都读 `0x60010000`、`reg 0x140010` 读 `0x3e8000c6`。已改成 `readone "$off"`。

  匀速的来源还没定，最像的解释是默认里 `wan.device=eth0` 之后 **udhcpc 在 eth0 上每隔几秒
  广播 DHCPDISCOVER**（一行 `pgrep udhcpc` + `logread | grep -c dhcp` 就能定，本轮没做）。
  注意这条推论同时说明：`0x20204` 与 `0x20210` 步进始终相等，它数的是**过 CPU 的东西**，不是过网线的东西。
- 因此 §20 末尾排的这套"改四个比特 → 看入口计数"**判不了**"整组还原能不能让收侧活"，
  判据本身是坏的。**xmacrx 的写入落地了（上表右两列证明），但结论要换仪表重做。**

**量到的第二条、也是这一节真正的收获：mainline 自己上电时读到的 XMAC0 就是通流的那套。**
两个开机（00:0x 的 run 189 RAM、00:21 的 run 185 flash）都打印

	lane pre-serdes: XMAC0 tx=0x60010000 rx=0x3e8000c6 frame=0x80000001 mode=0x00000000 duplex=0x00000100 misc=0x00002000
	lane after : XMAC0 tx=0x60010001 rx=0x3e8000c7 frame=0x80000000 mode=0x00000000 duplex=0x00000100 misc=0x00002200

- `zx279133-switch.c:2040` 前后那段"引导程序把 XMAC0 留在 0，每一个控制字都读 0x00000000，
  所以从来没人配过它"在这块板、这根线上**是假的**——它描述的线不在 LAN1 时的状态。

  mainline 重编之后状态字也没变好，它只是把 MAC 的成帧字和 PCS 的 AN 位动了）。

  `SOPC mac 1 never became ready (0x00000000); not publishing it`——**10-26 §15 说"mac1 ready 在
  提示符下读 0"这条在 Linux 侧同样成立**，驱动因此从不发布 mac1。

**下一步（顺序已经变了）**：仪表换成 `tools/ubingress.sh`（已排进下一个电源窗口）——同一批地址、

## 22. 00:45 不用上板的一条：原厂引导程序**只在它自己做网络动作时**才配 XMAC0，两簇 311 : 12 完全反相关

`tools/ubingress.sh` 00:41 那一轮在**刚进提示符**（还没做过任何网络动作）时 `md` 到

	19140000: 00000000 00000000 00000000 00000000
	19140010: 00000000 ...          19140020: 00000000 ...
	19020200: 00000000 ...（RED in/out、0x200b8、0x280180、0x280240 全 0）
	19143400: 00002000 00002000 00002000 00002000

而 §21 里 mainline 上电第一行读到的 `lane pre-serdes: XMAC0 tx=0x60010000 rx=0x3e8000c6
frame=0x80000001` 是**同一趟开机几分钟之后**的值。两边都对，差在时刻：**引导程序是开始网络会话
时才把 lane 拉起来的**（docs/19 记的 `xmac 0 speed set 2 in sgmii` 就是那个动作）。

把整晚的日志按这个字段聚合，两簇干净地分开（`grep -o | sort | uniq -c`，323 趟 mainline 开机）：

| `lane pre-serdes` | 趟数 | `XPCS0 status` | `XMAC link (nppt+0x84)` | XMAC0 `tx/rx/frame` |
|---|---|---|---|---|
| 正常冷启动 | **311** | `0x380b` → `(status&0x3800)==0x3800` **成立，走继承** | `0x0000` | **全 0** |
| 今晚我让 U-Boot 跑过 ping 会话的 | **12** | `0x2c03` → 掩码**不成立，走重编** | `0x0001` | `60010000 / 3e8000c6 / 80000001` |

**这一条把「改成继承引导程序就行了」这个补丁方向直接划掉。** 用户正常上电时继承不到任何东西：
311 趟里引导程序交下来的是 tx/rx/frame 全 0 的 MAC，`XMAC link` 也是 0——掩码 `0x3800` 恰恰只在
**这种**开机里通过。反过来，唯一有完整配方可继承的那 12 趟（也就是今晚被证明双向通的开机），
`0x2c03` 让驱动去重编。判据与有用的方向正好相反。

`switch.c:2059` 的继承分支现在也调 `zx279133_switch_xmac_configure(priv, true)`（:2064），
两簇的实质差别只在 PCS 编不编，所以真正缺的不是"要不要继承"，而是**没人知道引导程序那一次会话
到底写了哪些字**——`0x140000/0x140010/0x140020` 之外还动了什么（`nppt+0x84` 从 0 变 1、PCS 状态
从 `0x380b` 变成 `0x2c03` 都是那次会话留下的）。`tools/ubingress.sh` 下一轮因此改成量这个：
`pre`（刚进提示符）→ 板子自己 ping 两次（**既是拉起动作也是通流证明**，日志里必须有 `is alive`）
→ `pinged` → PC 单边 burst → `rxburst`，每个字给两个数：`pinged-pre` = 引导程序为了打开这条 lane
写了它吗（mainline 没有的那份配方），`rxburst-pinged` = 在一条**已证明通着的** lane 上，到底有没有
任何东西数从网线进来的帧（这也才是 §21 那句"换仪表"的落地）。

**顺带两条否证/自证，都要留档：**
- `md` 的行首是 `%08x`，会补前导零：`md 0x19028e0 4` 打的是 `019028e0: ...`。按 7 位前缀 grep 的两行
  （`0x28c4`、`0x28e4`）因此静默为空——与 §21 那个 `%06x` 是同一类假阴性，同一个脚本里已补零。
- 那一轮的"守卫"本身写错了字段（记录是 `UBIG <phase> <name> <value>`，值在 `$4`，我查了 `$3`），
  于是**把一份完整的 12 字捕获判成 BAD-PARSE 并交了回板子**，白烧一个约 20 分钟的窗口。守卫已在
  已知好的数据上重放验证（`10 of 12`，缺的两字正是补零那两个），并在注释里写明它现在防的是什么。
  `0x19143400` 一行四个 `00002000` 相同**未做解释**，只是原始形状。

## 23. 00:51 不用上板的一条：`VENDOR_FRAME_CFG` 这个常数和它自己的来源差一个 bit0

§21 记下"mainline 把通着的四个比特改坏了"，但没说清**它为什么这么写**。去翻常数来源，答案是
**一处转写错**，而且是本篇唯一一个"改一个数就能对齐三条独立证据"的点。

`zx279133-switch.c:110`：

	#define ZX279133_XMAC_VENDOR_FRAME_CFG	0x80000000

而这段 `xmac_program()` 抄的对象——恢复出来的原厂 mac 驱动 `staging/base/zx279133-mac.c:411-437`——
在同一个位置写的是：

	writel(0x00010000, xmac + ZX279133_XMAC_TX_CTRL);   /* 然后 SPEED_MASK=GENMASK(31,29) 塞 speed_code */
	writel(0x3e800086 | ZX279133_XMAC_RX_IPC, xmac + ZX279133_XMAC_RX_CTRL);
	writel(0x80000001, xmac + ZX279133_XMAC_FRAME_CFG);      <-- bit0 是 1
	writel(2, xmac + ZX279133_XMAC_MODE_CFG);
	value = readl(MISC_CFG); writel(value | BIT(9), MISC_CFG);

三条独立证据都站在 `0x80000001` 一边：

| | `FRAME_CFG` |
|---|---|
| 恢复源码 `staging/base/zx279133-mac.c:431` | `0x80000001` |
| 今晚通流开机交下来的值（§21 表 / 两个 boot 的 `lane pre-serdes`） | `0x80000001` |
| 2026-10-19 `xmac_test xmac_work_mode_set 0 2` 之后的签名（docs/92 §20 引 `staging/ctl/smac6.log` 的 A/B diff） | `0x80000001` |
| **我们仓库现在写的** | `0x80000000` ← 唯一不合的那一个 |

`staging/base` 的 `speed_code` 表也顺手解释了 TX_CTRL 的高三位：`SPEED_2500 → 6`
（`staging/base/zx279133-mac.c:396-406`），`GENMASK(31,29)` 塞 6 就是 `0x60000000`，加上
`0x00010000` 那一步 = `0x60010000` = 通流值；mainline 也是 `0x6001000x`，所以**速率编码两边本来就一致**，
不需要动。

**同一次比对里要记的两条反向结论**（免得下一个读的人把 `staging/base` 当成逐字正确的原厂码）：

- `staging/base` 的 `RX_CTRL` 那行算出来是 `0x3e800086 | BIT(9)` = **`0x3e800286`**，而通流开机读到的
  是 `0x3e8000c6`（= `0x86 | bit6`，**bit9 不在里面**）。也就是说这份转写在 RX_CTRL 上是错的，而我们
  仓库的 `VENDOR_RX_CTRL = 0x3e8000c6` 与实测一致——`switch.c:866-870` 那段注释说的"IPC 位 0x200 属于
  MISC_CFG，被误写进 RX_CTRL；RX_CTRL bit6 在原厂置 1 的地方被清掉"是对的，这次算是它的一个旁证。
- 唯一还没被解释的偏离是 `MISC_CFG`：`xmac_program()` 按原厂置 `BIT(9)`（我们也是），但**通流开机里
  它是 `0x2000`（bit9 干净），刚进 U-Boot 提示符时也是 `0x2000`**；mainline 编完读 `0x2200`。
  `0x2000` = bit13，像是上电默认。所以引导程序那次会话并没有把 IPC 位写进 MISC——**这是"原厂会话到底
  写了哪些字"这个问题上目前唯一一条与 `staging/base` 相反的证据**，下一轮 `ubingress.sh` 的
  `bring-up = pinged-pre` 那一列正是量它的。

**这条为什么重要**：它是本篇第一次出现"改一个常数就能同时满足三条证据"的补丁形状，而不是又一轮
运行时写寄存器。docs/65 §5 那个"帧被交给 RED 时长度是 0"的形态，如果成立，最自然的归属就是这个成帧字。
但**先别推**：它能不能让收侧活，要等 `ubingress`（通着的 U-Boot 里到底有没有东西数网线帧）和
`lineth0ping`（挂上 eth0 的地址后能不能被 ARP 到）这两个读数；`§21` 已经证明现在手上那把芯片尺不灵。

## 24. 更正 §23：FRAME_CFG 的 bit0 是**原厂自己两个产物互相矛盾**，我们抄的那一边有反汇编撑着

§23 写成"三条独立证据都站在 `0x80000001`，我们仓库是唯一不合的那一个"——**这句夸大了**。把常数来源
的原始凭证翻出来（`staging/ctl/re-xmac0.md:284`、`re-vendor-module-reg.md:531`，也已经在 docs/35 的
B10 行登记过）：

	0001a258  mov w2, #-0x7fffffff          ; = 0x80000000
	0001a260  str w2, [x1, x0]              ; XMAC0 + 0x20 FRAME_CFG

`np_133.ko` 的 `xamc_init_conf_by_speed()` 里 FRAME_CFG 的字面量**就是 `0x80000000`**。也就是说
`ZX279133_XMAC_VENDOR_FRAME_CFG = 0x80000000` 是对原厂 .ko 的**忠实转写**，§23 引用的 `switch.c:102-107`
那段"厂商清、我们置"的注释才是错的那一侧（它把恢复出来的 C 代码当成了原厂值）。

于是这件事的真实形状是**原厂自己的两个产物互相矛盾**：

| 来源 | FRAME_CFG bit0 |
|---|---|
| `np_133.ko` 反汇编 `0x1a258`（原厂 Linux 模块） | **0**（`0x80000000`）← 我们抄的就是这个 |
| `staging/k/zx279133-rtl8372n.c:2765`（树里恢复的 C） | **1**（`0x80000001`） |
| `staging/base/zx279133-mac.c:431`（另一份恢复 C） | **1** |
| 2026-10-19 `xmac_test xmac_work_mode_set 0 2` 之后实测 | **1** |
| **2026-10-26/27 通流 U-Boot 会话交下来（两个 boot 的 `lane pre-serdes`）** | **1** |
| 原厂 4.19 在跑时的实测 | **0**（`switch.c` 的注释：那几个字"reset 后没再写过"，读 0） |

同一张表里 RX_CTRL 那一列的对照结论也要跟着改口径：反汇编 `0x1a240` 给 `mov w2, #0xc6; movk w2,#0x3e80,
lsl#16` = `0x3e8000c6`，**与今晚通流 U-Boot 读到的完全一致**，而两份恢复 C 写的是 `0x3e800086|BIT(9)` =
`0x3e800286`。所以 RX_CTRL 上是 `.ko + U-Boot 实测` 对 `恢复 C` 不一致，我们的常数站对了；
FRAME_CFG 上是同一组来源不一致，我们的常数站在 `.ko` 那边。

**结论要老实说：这一位不能靠"读代码"定，只能靠板子。** 而这正是今晚已经做完的那半步——
`tools/xmacrx.sh` 把四个 MAC 字**整组**改成通流开机交下来的值（含 FRAME_CFG `0x80000001`），四次回读
证明写进去了；判它生死的是 `tools/lineth0ping.sh`（给 eth0 挂一个只有它有的地址，看能不能被 ARP 到 /
`eth0 rx_packets` 动不动）。**在那两个读数出来之前不推这个常数**——§23 里"改一个数就能对齐三条证据"
这句话按本节更正后作废，它实际是"改一个数去赌原厂两个产物里哪一个才是活的那条 lane 用的"。

## 25. 撤销 §23/§24 留下的"常数错"这个候选：`re-xmac0.md` §3.7 早就逐字对过，我们写的与 `np_133.ko` 全等

§23 说"一处转写错"、§24 更正成"原厂两个产物互斥"——**两句都还留着一个不该留的候选**，因为翻
`staging/ctl/re-xmac0.md` §3.7（10 月做的、已经落盘的逐指令对照）才发现它早就回答过：

| XMAC0 偏移 | `np_133.ko` 的指令 | 厂商值 | 我们驱动的值 | 结论 |
|---|---|---|---|---|
| `+0x000` TX_CTRL | `0x1a220/0x19d20/0x1a0a0` | `0x00010000` → 塞 speed → `\|=1` | 同 | **match** |
| `+0x010` RX_CTRL | `0x1a24c/0x1a0ec` | `0x3e8000c6` → `\|=1` | `0x3e8000c6` | **match** |
| `+0x020` FRAME_CFG | `0x1a260` | **`0x80000000`** | `0x80000000` | **match** |
| `+0x280` MODE_CFG | `0x1a27c` | `2` | `2` | **match** |
| `+0x500` DUPLEX | `0x1a150/0x1a154` | `(v&0xfeffffff)\|0x01000000` | `v & ~BIT(24)` | **match** |
| `+0x3400` MISC_CFG | `0x1a288` | `\|= 0x200` | `\|= BIT(9)` | **match** |
| `0x2c0004` | `xmac_reset()` `0x1a044` → `smac_reset(0x400)` | bit10 = XMAC0 复位 | `BIT(10)` | **match** |

那张表的最后一句就是本节要的：**"Our driver writes every one of these exactly as the vendor does."**
所以 `ZX279133_XMAC_VENDOR_FRAME_CFG = 0x80000000` 不是抄错，它与原厂 Linux 模块逐字一致；
`staging/k`、`staging/base` 那两份恢复 C 写的 `0x80000001` 是**另一个来源**（恢复质量本身在
`RX_CTRL` 那行已经被证明不可靠：它写 `0x3e800286`，而 `.ko` 与今晚 U-Boot 实测都是 `0x3e8000c6`）。
**"改一个常数"这个候选到此撤销**，§23/§24 的两种说法都不再需要。

同一张表里更该被记住的是它顺手量到的**读侧形状**（原文照抄，别重新发明）：

| 寄存器 | 写入 | 回读 | 判定 |
|---|---|---|---|
| TX_CTRL | speed 位 + `\|=1` | `0x60010001` | sticky（bit0 硬件也置） |
| RX_CTRL | `0x3e8000c6` + `\|=1` | `0x3e8000c7` | sticky（bit0 硬件也置） |
| FRAME_CFG | `0x80000000` | `0x80000000` | sticky |
| **MODE_CFG** | `2` | **`0x00000000`** | **拒绝写入** |
| **DUPLEX** | bit24 | **`0x00000100`**（是 bit8，不是我们写的 bit24） | **拒绝写入，且读到的位与写入无关** |
| MISC_CFG | `\|=0x200` | `0x00002200` | sticky（bit9 是我们加的，bit13 本来就在） |

两个寄存器干脆不接受写，而 DUPLEX 回读到的是一位完全无关的 bit8——那一节自己给的结论是
**"这是一个不是我们所认为的那块寄存器的块，或者同一个窗口有第二份重叠映射"**。这条与今晚
`0x19143400` 一行读出四个相同的 `00002000`（§22）是同一类征兆，谁也不要把它当"某个字段"来解释。

**因此嫌疑列表变成这样**（"常数"划掉后）：
① **顺序/时序/复位**：我们的 `xmac_configure()` 与 U-Boot 会话对同一个 MAC 做**同样的值**，但通流
开机里 `frame` 最终读到 1、`XMAC link(nppt+0x84)` 读到 1，而我们编完读到 0/0；差别只可能在**谁先谁后、
复位脉冲的宽度、以及 SOPC 那一步**（`re-xmac0.md` §3.6 记的 publish 轮询与 `0x343f0` 那位）。
② 在一条**通着的** lane 上把 8226 声明成交换机口（§11 的否证做在被 mainline 重编过的 lane 上，条件不足）。
③ 把 eth0 挪到 XMAC0（`mac.c` 三处基址 + `BIT(11)→BIT(10)` + `pcs-handle` + 让 `switch.c` 让位）。
① 的读数就是排在路上的 `ubingress.sh`（`bring-up = pinged-pre` 那一列直接给出"会话写了哪些字"），
② 的判决是 `lineth0ping.sh`（挂地址后被不被 ARP 到）。

| `0x280240` IDM RX ptr | 0 | 3 | **3** | 7 |
| `0x28c4` / `0x28e4` USCH | 0 | 0 | 0 | 0 |
| `0x200b8` / `0x200bc` | 0 | 0 | 0 | 0 |

**量到的第一件（也是 §22 欠的那张配方表）：原厂引导程序在自己的会话里现场写这三个字，且只写这三个。**
`pre` 全 0 → `pinged` 出现 `60010000 / 3e8000c6 / 80000001`，一次 ping 而已。同时：

- **`MISC_CFG` 它没碰**（`0x2000` 四段不变）。我们驱动的 `xmac_program()` 结尾 `MISC |= BIT(9)`
  是**多出来的一步**（§25 那张"与 .ko 全等"的表里 `0x1a288` 那行确实存在，但**活的那条 lane 不用它**）。
- **TX_CTRL 和 RX_CTRL 的 bit0 在通着的 lane 里是 0。** 我们驱动写完读回的是 `...0001` / `...00c7`。
  §21 就注意到这个方向可疑（"通流的开机 bit0 是清的"），这一轮是**第一次看着它被写下去**，
  不是在提示符上抄遗留值，所以 `bit0 = enable` 这个本仓库沿用了很久的解释，在这条 lane 上
  **与原厂的动作相反**。
- `FRAME_CFG` 是**被写成 `0x80000001` 的**（bit0=1），当场量到，不是继承来的遗留值。
  这把 §25 撤销"常数错"时留下的那句"只能靠板子定"补完了：`.ko` 里是 `0x80000000`，
  而**今晚真的在通流的这份代码写的是 `0x80000001`**——所以 §23/§24 争的那个 bit 从此不再是"两个来源互斥"，
  是"**.ko 不是这条 lane 的驱动者**"。

**量到的第二件，把入口计数这条路彻底关门：** 在一条**同一轮里刚被证明双向通着**的 lane 上，
PC 单边发给它的 **60 帧广播没有让表里任何一个字动**（`rx-only = +0`，连 `0x20204` 都是 0，
`0x28c4/0x28e4` 与 `0x200b8/0x200bc` 四段全 0）。而板子自己 ping 两次让它们动了 +24，
再 ping 一次动了 +32——即 `0x20204/0x20210` 与 `0x280180/0x280240` 数的是**板子发出去的那一侧**。
注意 `after` 段的 +32 摊在 32 s 里、`pinged` 段的 +24 摊在 28 s 里（≈1 字/秒），
所以那 +32 不是"burst 迟到"，是同一条匀速的背景；而 `pre→pinged` 之所以是 +24，
是因为会话一开就有背景活动——**这批字与"网线进来的帧"之间没有关系，在原厂代码里也没有。**

⇒ **docs/65 §4-5 那批计数器从今天起不能用于任何"收到了"的断言**（U-Boot 与 mainline 两边都试过了）。
本篇里"到达"这件事至今只有一个仪表成立过：**PC 自己的网卡计数**（`is alive` 与 `rx_delta`——
板子发出来的东西会到 PC），以及**板子能不能被 ARP 到 / `eth0 rx_packets` 动不动**。

**由此，补丁方向第一次变成确定的那一类。** 把 §26 的三件事摆在一起：

1. 通着的 lane = 这三个字 + **不要** bit0 + **不要** MISC bit9 + `FRAME_CFG bit0=1`；
2. `xmacrx.sh` 已经在运行中的 mainline 里把这四个字写成了**与通流开机逐字节相同**（四次回读为证），
   而写完之后 PC 的 `rx_delta` 仍然 80 s 全 0（§21 末）；
3. mainline 下 `eth0` 的发是 `mac.c` 走 **XMAC1** 的环，收也是 XMAC1 的环（`mac.c:31/413/447`），
   而**这条 lane 的 MAC 是 XMAC0**。

第 2 条不是"MAC 字没用"的证据——它只是说明**在 mainline 里改这四个字永远看不到板子发出去**，
因为发方向根本不由 XMAC0 承担。真正缺的是**让这条 lane 的收发都归 XMAC0**，也就是
**把 RTL8226 声明成交换机的一个 SPA 口（SPA 5），让它和 LAN2/3/4 走同一条已经修好的路**：
收有去处（DSA 口 → br-lan），发由 `switch.c` 已经正确驱动的 XMAC0 出去。
§11 当年否证的是"在一条已被 mainline 重编过的 lane 上声明"，**这一轮把那个条件补上了**
（声明 + 通着的 lane 现在是同时可得的），所以它不再是禁区。

## 27. 01:07–01:16：MAC 字整组写成通流形状之后，**两个方向仍然都是死的**——而我把"收方向活了"讲错了一次

这一节有两个部分，第二部分是对第一部分的更正。**最终形状只认 01:15 那组带分隔符的读数。**

**做过的实验（同一个 flash boot，run 185，线在 LAN1）**：`tools/xmacrx.sh` 在 01:09:38 把四个 MAC 字
写成 §26 从**活的** U-Boot 会话上量到的形状，四个都 `VERDICT WRITE-TOOK`（`readone` 修好后第一次有
真回读）：

	0x140020 0x80000000 -> 0x80000001   0x143400 0x00002200 -> 0x00002000

然后 `tools/lineth0ping.sh`（给 `eth0` 挂一个只有它有的 `192.168.9.2/24`，PC 绑 `192.168.9.25` 去 ping）、
`tools/lan1sopc.sh`（读/拨 XMAC0 的 SOPC send）、以及 01:15 的哨兵复量。

**我讲错的那一句**：01:07 与 01:10 两次 `lineth0ping` 都打印 `eth0 before rx=00 tx=065` /
`eth0 after rx=10 tx=1121`，我据此说"**收方向是活的**（ARP 广播进到了 eth0 的环）"。**这句作废。**
错在取值：`num()` 用 `grep -ao 'T0RX=[0-9]*' | tail -1`，而 `T0RX=0` 这行在**中继回显**里被截断重排过

抓到的数字不是 counters 本身——`rx=00`、`tx=065` 这种**带前导零的形状**就是它的自证，sysfs 不打前导零。

	L3A=0-227        # ping 之前

⇒ **`eth0 rx_packets` 是 0，两次都是 0。** 收方向**没有**活。发方向照旧是"计数涨 16 个、PC 一个字节都
没收到"。**结论：把 XMAC0 的四个控制字写成与通流开机逐字节相同，mainline 下这个口两个方向都不通。**
§20/§21 追的那条"四位差"到此**否证**（这是否证，不是没测——写入有四次回读、激励有 PC 侧 `tx_delta`
尖峰、计数器有分隔符格式）。

`lan1sopc.sh` 那一段顺手量到的形状，记下来免得再猜：

	nppt+0x342c0 (XMAC0 SOPC send)  before=0x00000001  after=0x00000001
	nppt+0x342c4                    before=0x00000001
	nppt+0x342a4 (mac0 ready)       before=0x00000000  after=0x00000000
	nppt+0x342a8 (mac1 ready)       before=0x00000001  after=0x00000000   <-- 会自己变
	nppt+0x34100                    0x00000000

也就是 **`0x342c0` 在 mainline 下本来就是 1**（不用拨），`0x342a8` 在两次读之间从 1 变 0——
这既说明 §22 那条"SOPC `mac1 ready` 在提示符下读 0、Linux 侧读 1"是真的，也说明这两个字**不是**
锁存的状态位。谁要拿它们当判据，得先承认它们会自己动。

**还剩什么**：MAC 字（§20/§21/§26）与 SPA 声明（§11）两条都已被正面否证，PHY 侧已关（§17），
入口计数不是尺（§21/§26）。**唯一从没在"通着的"和"不通的"两个开机之间对比过的，就是 SoC 侧那份
SerDes 镜像**（`0x16100000` 块，mainline 读不到、U-Boot 能读）：docs/92 §15 留过一条未解释的差
（U-Boot `0x161000d0 = c880bb83` vs mainline 打印的 `c87fbb83`，只差 bit 8/9 那一带），
而 `phy-zx279133-uni-serdes.c` 里那份 49 字 profile 与 np_133 恢复版只有 21/49 相符。
`tools/ubserdesimg.sh`（01:17:20 已上膛，等 ~01:21 的沿；它先 `ping` 并要求 `is alive` 才取镜像，
所以取的是**通着的**那份）+ `tools/serdesimgdiff.py` 就是拿这个的。

**方法上带走一条**（已写进 `tools/lineth0ping.sh` 的教训里）：从串口日志取一个数，**必须让那行带自己
的分隔符**（`echo NAME=$(cat a)-$(cat b)`），不能靠"名字=值"的行尾形状——中继回显会把长命令折行，
折出来的半行正好形如 `NAME=<别的数字>`。这一类比 `%06x` 更阴，因为它给出的是**看起来合理的错数字**，
不是空值。

## 28. 01:22 窗口：SoC 侧 SerDes 也关掉了——mainline **根本不重写**那份镜像，而那个"未解释的差"是只读状态

`tools/ubserdesimg.sh` 在 01:21 那个沿抓到 U-Boot，**先 ping 并要求 `is alive`（本轮 =1）**再取
`0x16100000` 块的 0x00..0x130，落到 `staging/ctl/ubserdesimg.txt`；
`python3 tools/serdesimgdiff.py` 对着 `phy-zx279133-uni-serdes.c` 的 `zx279133_uni_1g_profile[]`
数出 **28 个字不同**——与 mainline 自己打印的 `image differs in 28/49 word(s)` **一字不差**，
所以两边的解析都对。

然后是这一节真正的判决，来自驱动源码而不是板子：`phy-zx279133-uni-serdes.c:203-215` 在链路已起的
分支里**只做比较、然后 `goto out_unlock`**，既不做 `reset_pulse` 也不做 `write_profile`（那两个在
:218-222 的另一条路上）。今晚每一趟启动打印的都是这条：

	Uni SerDes 1G inherited: mode 0x101 already, image differs in 28/49 word(s), status 0xc880bb83/0x1000706

⇒ **`28/49` 是"活块 vs 我们那张表"的差，而这张表在这条分支里一次都没被写进块。** mainline 拿到的是
引导程序留下的镜像**原封不动**，所以 §15/§17 之后剩下的最后一条"SoC 侧 SerDes 内容不同"也关门了。
（对照另一颗口：`mode 0x1 already, image differs in 0/49` — 那条口块与表全等，说明比较本身有效。）

顺带结掉 §15 那条挂着的不一致：同一个地址 `0x161000d0` 在几趟开机里读到过
**`c880bb83` / `c87ebb83` / `c87fbb83`** 三个值（差别在 bit16..bit21 这一段）。
**一个自己会变的字是只读状态/自适应字段，不是配置**，谁都不要再把它当"引导程序与内核写了不同的值"。
`0x161000e4 = 01000706`（RX LOS 清）两边一致，与 §15 相同。

**至此今晚的排除表**（每条都有正控制）：PHY 侧全等（§17）、SerDes 镜像 mainline 不动（§28）、
XMAC0 四个字写成通流形状仍双向不通（§27，写入有四次回读）、SPA 口声明单独无效（§11）、
入口计数不数网线帧（§21/§26，U-Boot 与 mainline 两边都试过）、`0x342c0` 本来就是 1（§27）。
唯一还站着的结构性事实是 §18/§27 那条：
**mainline 下 `eth0` 的收发环都挂在 XMAC1 上（`zx279133-mac.c:31/413/447` + 复位 `BIT(11)`），
而这条 lane 的 MAC 是 XMAC0**——引导程序证明过 XMAC0 才是会数这根线的块（§26：一次 ping 就把
`60010000/3e8000c6/80000001` 写下去并把 `nppt+0x84` 变成 1）。
所以补丁的形状只剩一个：**把 eth0 的 MAC 从 XMAC1 挪到 XMAC0**（三处基址 + 复位位 `BIT(10)` +
DTS 的 `pcs-handle` + 让 `zx279133-switch.c` 不再占 XPCS0/XMAC0），并在 RAM 里判。
`lan-cpu0` 不是这条 lane 的用户（docs/44：它是 IDM netdev，SPA CPU 15），所以这个改动有理由不动
四个 UNI 口的通路——**但这是推断，必须在 RAM 里连同 `g4verify`/四口 jack-walk 一起回验**，
因为如果 `switch.c` 对 XMAC0 的编程真的撑着什么，退化会立刻现形。

## 29. 01:26 窗口：**「通流形状的 MAC 字 + SPA 口声明」这个组合也被否证**——两条嫌疑第一次也是唯一一次同时成立

§11 与 §27 各自的否证都留下一个缺口：§11 做声明的时候，MAC 四个字是 mainline 自己写的形状；
§27 把四个字写成通流形状的时候，**没有任何 SPA 口被声明**，帧收上来也没去处。这个组合今晚第一次
被做出来，用的就是为它写的 `tools/lan1declare.sh`（`MEM=5`，源口 = `SRC=1` 那个能用的口）。

量到的（同一个 flash boot，`01:25:48`–`01:28:37`，**12 次写入全部带逐字回读**）：

	MAC   0x140000 -> 0x60010000   0x140010 -> 0x3e8000c6   0x140020 -> 0x80000001   0x143400 -> 0x00002000
	SPA   mem 5 的 addr 0/1/10/13/14/17/18/19 = mem 1 在同一次开机里的现读值
	      (0x0000a6a5 0x0000088f 0x0fa0000e 0x00008008 0 0x04400410 0x00400840 0x96040001)  逐字回读一致
	再 `fa 5 0x960c0001`（MF 扩展表那份属性字）与 `trapall 5 2`（该口全部协议 trap 到 CPU）

判决：**PC 绑源地址 ping `192.168.9.1` 十二次，`0 echo replies`，邻居表 `Incomplete`，
`lan-cpu0 rx` 与 `br-lan rx` 的差都是 0。** 激励这边有 `tx_delta` 尖峰做正控制（§21 末同法）。

⇒ §11 与 §27 之间的缺口已经补上并关掉：**"把 8226 声明成交换机的口" + "MAC 字写成通流形状" 两件事
同时做，也不能让 LAN1 在 mainline 下通。** 本篇标题（"那个 2.5G 丝印口是主线从未声明的交换机口"）
到这里已经是**第二次**被自己的实验否证，且这次的条件比第一次严格。

**那还剩下什么。** 芯片里能被寄存器写到位的部分（MAC 控制字、SPA 表、MF 表、trap 表）现在全部与
"通着的"状态逐字相同，而线还是不响应；PHY 侧十个 CL45 字全等（§17）、SerDes 镜像 mainline 原封不动
继承（§28）、`0x342c0` 本来就是 1（§27）。**唯一从没被对比过的，是帧与队列之间的绑定关系**：
U-Boot 会话一次 ping 就让 XMAC0 的发送计数从 2 涨到 11（§15），说明原厂把它的描述符挂到了 XMAC0 这一侧；
mainline 的 `eth0` 把环挂在 XMAC1 上（`mac.c:31/413/447` + `XMAC1_SOPC_SEND_ENABLE = 0x342c4`），
所以我们写对 MAC 字也不会有帧进 XMAC0 的队列——**这不是 MAC 的寄存器问题，是 NP/IDM 的 ring→port 绑定问题**。
下一个读数因此是 U-Boot 里那条通着的 lane 的 `idm_tx_debug` / `idm_rx_debug` 描述符（原厂 CLI 自己会打印
在用的描述符，见 docs/19/HANDOFF 的 U-Boot CLI 一节），与 mainline 给 `eth0` 编出来的描述符逐字段比。
**在此之前不出包**：现在推一个构建回答不了任何新问题，只是占住构建机。

**四块全零，包括本该非零的 mem 1（LAN2，通着的口）——所以这是仪表错，不是判据。** `er` 的第一个参数
是**绝对 ERAM 块号**（`zx279133_smmu0_read(eth, block << 7, …)`），而本驱动的 ERAM 表基址是 probe 时
**从 0x3000 顺序分配**的（np.c:4406 `u32 eram_base = 0x3000;`，注释写明 0x3000 以下根本写不进 ERAM）。
§48.3 把 `{0x7d,1,0x3,0x40}` 里的 `0x3` 当成了“基块 3”，它其实是**每条位宽索引**（`zx279133_se_sdt_bit_len[3]`
= 128 位，np.c:4132/4139）。所以 `er 4/8/9/18` 读的是非 ERAM 地址，回零是必然的。

正确的入口是 debugfs 自己打印的那张表（`grep -A60 ERAM $D`，本次启动）：

	  0x7d   24737  128

⇒ mem n 的块号 = **24737 + n**。这也再次演示了本项目的规矩：**没有正控制的零不能当否证**
（mem 1 的零就是那个正控制）。

### 49.3 §48.3 的前提被代码否掉：mem 5 的镜像**是 mainline 自己写的**，写的就是 0x00042000

`zx279133_lan_port_bringup()`（np.c:3914）在 RTL8372N 的 LAN-lane 形状里同时写两处：

	zx279133_spa_indirect_write(eth, 5, 19, 0x00042000);   /* SPA 内存 */
	zx279133_mf_eram_attr_set(eth, 5, 0x00042000);         /* 0x7d 镜像，word0 */

而且它写进的 base 是**只有 mainline 的 probe 才会分配**的那个（引导程序不可能知道 24737 这个号），
所以「镜像条目从来没有被 mainline 写过」不成立：**它是被写过的，写的是 RTL8372N 路径的值**。
mem 5 与 mem 1 不同也因此在预料之中——驱动把 mem 5 当成“LAN-lane/CPU 侧”，不是 UNI jack。

§48.4 的第一分支（“与 mem 1 不同 ⇒ 漏写”）因此**作废**。现在真正没定的是**mem 5 该用哪个值**：

- 本驱动的说法：0x00042000 是原厂 LAN-lane 形状（code comment）；
- docs/27 §3.1 的旧说法：厂商给 mem **1..5** 都是 `0x96040001`（那一轮正是据此把 c1da3fa 的镜像修好）；
- 两者不可能同时成立，而**谁也没在真正通流的原厂系统里读过 mem 5 的 0x7d 条目**（§11 读的是 mainline
  自己的闪存启动，§37 的 U-Boot 属性表又是“属性号≠SPA 字”的陷阱）。

### 50.4 顺带查出来的两个工具坑（都会让人误判）

1. **`reg` 动词必须写十六进制前缀。** `np.c:1214` 用 `kstrtou32(tok, 0, &off)`，base 0 ⇒

## 51. 17:25–17:56 那次开机：把断点钉死在 **PHY 与 XMAC0 的 RX 之间**

### 51.0 这一轮的结论一句话

**PC 发进来的帧连 XMAC0 的接收统计字都没碰到**（RX 计数器组在一次 6 帧突发的前后**逐字相同**），
而同一时间 XMAC0 的**发送**统计字在涨 ⇒ **XMAC0 就是通往 PC 那条路上的 MAC**，
断点既不在 PC 侧、也不在 9132 里、更不在 PHY 的寄存器上，**就在 SoC 这一侧的 lane 上**
（Uni SerDes / XPCS0 / XMAC0 的 RX 那一半）。

### 51.1 两次开机，两次复现同一件事

| 轮次 | 绑定 | eth0 rx_packets | PC ping 回复 | PC rx_bytes | PC 的 ARP 表 | 板子 ping PC |

**单向，且是硬件级的单向。**

XMAC0 的统计块在 NPPT+0x142000（`reg 0x142000` 起一片 dump）。17:51:01（突发前）与

### 51.4 lane 的链路字：主线下是 **down**，原厂是 **up**——而守门逻辑没生效

`reg 0x90`（= `ZX279133_NPPT_XPCS0_STATUS`）本轮实测 **0x00002c03**。
`switch.c` 自己的判据是 `(status & 0x3800) == 0x3800` ⇒ **down**；
U-Boot 里量到的是 **0x380b ⇒ up**。

`switch.c` 里本来有一道守门：
> “If the PCS still says the link is up, the bootloader brought it up … so in that case the
> bootloader’s configuration is adopted as it is.”

**本轮这道门没生效**：开机日志里第一条 lane 快照就是
`[1.600528] lane pre-serdes: XPCS0 status=0x2c03 link=down`，
**在 `switch.c` 自己动 PCS 之前**就已经是 down 了。
⇒ **断电到 1.6 s 之间有别的东西把这根 lane 弄 down 了**，守门逻辑看不到这种 down，
于是驱动按“link 没起来”的分支把 PCS 按 1G SGMII 重写了一遍——**在一个本来就 down 的 lane 上再写一次**。

### 51.5 §50.5 第 4 步（flood 字）**FAIL**，这一支关掉

mem 5 的 SPA 17/18 现在是 **0**，mem 1（一个能用的口）是 `0x04400410` / `0x00400840`。
把 mem 1 那两个值原样写进 mem 5（读回确认：`9132 spa: mem 5 addr 17 = 0x04400410`、
`addr 18 = 0x00400840`），再打一组 PC 帧 ⇒ **eth0 rx 仍然 0→0、PC 仍然 0/6**。
⇒ **“mem 5 缺泛洪/转发向量”不是断点**，§48.4 第二分支与 §50.5 第 4 步**一并关掉**。

### 51.6 lane 被按 **1G** 编程，而树里另一处把这根 lane 当 **USXGMII** 用

`switch.c` 的 `priv->usxgmii` 只有在 Uni SerDes **拒收 SGMII** 时才置 true；
本轮开机日志是
`zx279133-uni-serdes 16100000.phy: Uni SerDes 1G inherited: mode 0x101 already, image differs in 28/49 word(s)`
⇒ **SGMII 被收下了** ⇒ `usxgmii = false` ⇒ `zx279133_switch_xmac_program(priv, ZX279133_XMAC_SPEED_1G)`,
**XMAC0 的速度字（bit31..29）= 3 = 1G**（`0x60010000` 的 0x6 正是 `011`）。

而同一棵树的 `zx279133-rtl8372n.c`（`zx279133_lan_xpcs_configure()`）
**把这同一个 XPCS0 / 同一根 Uni SerDes lane 按 USXGMII 10G 配**，
`switch.c` 的 `zx279133_switch_xpcs_usxgmii()` 就是照抄它：
`VEND2 AN_CTRL` 清 `BIT(3)|BIT(8)`、`PCS MDIO_CTRL2 = 0`、
`PCS DIG_CTRL1` 置 `USXG_EN(BIT(9))|VSMMD1_EN(BIT(13))`、
`PCS KR_CTRL(0x8007)` 清 `GENMASK(12,10)`、`DIG_CTRL1` 置 `VR_RST(BIT(15))` 后轮询清零、
`VEND2 AN_CTRL` 置 `AN_INTR_EN`、`VEND2 BMCR = 0x3140`。
**USXGMII 对应的 XMAC 速度字是 0**（`ZX279133_XMAC_SPEED_USXGMII = 0`）。

另外，`docs/07` 里从 `plat_132.ko` 还原出来的**原厂 1G** 配置是
`xpcs_1g_mode_conf(xmac, speed=3, duplex=1, pcs_mode=2)`——**speed=3 与主线一致**，
所以速度字本身不能单独判为错；**但“原厂在另一个驱动里把这根 lane 当 USXGMII 用”这件事，
是本轮读代码读出来的最大的一条新线索。**

### 51.7 顺带查出来的两个工具坑

1. **`trapall` 动词必须带 port 参数。** `np.c:1691` 要求 `port <= 7`，
   只写 `echo trapall >$D` 会得到 `ash: write error: Invalid argument`（`-EINVAL`）。
   它**不是 dump，是一个写动作**：把 port 的 128 个协议项全设成某个 action
   （`action` 省略时是 2 = trap 给 CPU），而且**只写 group `port<<7` 一组**（不像 `proto_init`
   那样同时写 0x00/0x10/0x20 三个 bank）。
2. **`tools/bootflashram.sh` 的 `pkill -f 'tools/armu.sh'` 在 MSYS 上永远匹配不上**
   （`ps -W` 只显示解释器 `/usr/bin/sh`，不显示脚本名）。
   **后果**：预置的 `'u'` 流在整场窗口里一直活着，**每 0.25 s 往 `sercmd.txt` 写一次 `u`**，
   于是**任何排在它后面的命令都被吃掉**——本轮 17:26 的 `TP=`/`TR=` 两个身份命令就是这样
   消失的，17:26:36 之后控制台上一律是 `-ash: u: not found`。
   **已改**：改成记下 `$!` 并在抓到 U-Boot 提示符后 `kill "$ARMPID"`（17:46:09 实测
   “stream stopped”，之后控制台干净）。

### 51.8 预登记：下一个窗口（18:05 那次开机）怎么走

按“先分清两个开关、再动一个变量”的顺序，判据全部写死：

0. **基线（正控制）**：`xmac=0`、`tx_port=5`、`ip addr add 192.168.9.3/24 dev eth0`
   ⇒ PC 必须继续收到帧（`lan1direct.sh` 的 `PC rx_bytes` 增量必须 > 0）。
   **不动就是仪器坏了，不是板子坏了。**
1. **lane 链路字的守门**：在**任何写入之前**先读 `reg 0x90`，记下是不是 `0x2c03`。
   再读 `reg 0x140000`（XMAC0 TX_CTRL，速度字在 bit31..29）与 `reg 0x140010`/`0x140020`。
2. **RX 计数器的持续见证**：每次都把 `reg 0x142010`（RX 那 16 个字）与 `reg 0x142070`（TX 帧数）
   各读一次。**RX 那 16 个字只要动了一个，RX 就通了**——这是本轮新立起来的、不会被
   “上层没认领”污染的见证。
3. **实验 A（单变量）：XPCS0 恢复原厂那五个字。**
   `switch.c` 的 1G SGMII 档把 `VEND2 AN_CTRL` 从原厂的 `0x0005` 写成 `0x0015`。
   **把 AN_CTRL 写回 `0x0005`，再读 `reg 0x90`**：链路字若回到 `0x38xx` ⇒ 就是这一位。
   （XPCS0 没有 debugfs 通道——`m45` 动词只通到 `zx279133,outer-phy-bus`，
   `switch.c` 也没有自己的 debugfs；**若这一条做不到，就要给 `switch.c` 加一个
   `xpcs` 写动词再出 CI 包**。）
4. **实验 B（单变量）：lane 按 USXGMII 跑。**
   `regw 0x140000 0x20010001`（速度字 3 → 0，保留 bit16 与 bit0），
   再按 §51.6 那串 USXGMII 配方改 XPCS0，**然后读 `reg 0x90` 与 RX 计数器**。
   **判据**：链路字变 `0x38xx` 且 RX 计数器动 ⇒ 断点就是“lane 被按 1G 编程”。
5. **实验 C（单变量）：`XMAC0 frame` 的 bit0。**
   `regw 0x140020 0x80000001`（把 `switch.c` 清掉的那一位写回去），再打一组 PC 帧。
   原厂留下的就是 `0x80000001`，而 `switch.c` 写的是 `0x80000000`。
6. **实验 D（若 A/B/C 都 FAIL）：把 9132 的 port 5 用 `trapall 5 2` 明确 trap 给 CPU**，
   并用 `trapall 1 2` 做正控制（mem 1 是能用的口）。

**这一轮仍然不派 CI 包**：RX 的候选已经收窄到
**“lane 的 PCS/速率档”** 与 **“XMAC0 的 RX 侧开关位”** 两处，
两处都能先用运行时的寄存器写去试，**试不出来再改代码**——一个包只该回答一个问题。


## 52. 断点终于被夹住了：帧到了 XMAC0，进不了 IDM（2026-10-27 21:33-22:27）

### 52.1 帧确实到 XMAC0，而且是“好”的帧

用 PC 发 2000 个 1000 字节的广播 UDP（2 MB）做量具，板子自己数自己的寄存器：

| 计数（XMAC0 相对） | 发之前 | 发之后 | 差 |
|---|---|---|---|
| 0x2400 RX 总帧 | 0x1619 (5657) | 0x1e02 (7682) | **+2025** |
| 0x2440 RX 好字节 | 0x8090ab | 0xa08442 | **+2 101 783** |
| 0x2460 RX 好广播 | 0x0d (13) | 0x7f6 (2038) | **+2025** |
| 0x24a0 CRC 错 | 0 | 0 | 0 |

**PC 的字节数与板子数到的字节数逐字节对上。** 所以
“帧没到 MAC”这一层是通的；**§51 之前量到的“XMAC0 计数器动了”是 TX 侧的字
（0x142000-0x1423ff 是 TX 块，RX 块在 0x2400 起）**，
“帧没到 IDM”这一层也没通——三处独立证据：

1. 驱动的单帧捕获（`rxb`，“下一帧收到就打印”）在 2000 帧之后**一个字都没有**；
2. **全部 16 个 IDM 队列**的头（`rxd <q> 2`，q=0..15）的 address/length/metadata 全是 0；
3. `eth0` / `br-lan` / `lan-cpu0` 的 rx 包数全是 0。

**所以断点在 XMAC0 的 MAC 核与 IDM 之间，是硬件/配置层面的。**

### 52.2 新证据：SOPC 的 ready 位，XMAC0=0 而 XMAC1=1

NPPT+0x342a0 那一块（SOPC）实测：

```
0x342a0 = 0    0x342a4 = 0   <- XMAC0 ready（只读状态，写 1 不生效）
0x342a8 = 1                    <- XMAC1 ready
0x342b0..0x342cc = 1           （0x342c0 = XMAC0 send-enable = 1，0x342c4 = XMAC1 = 1）
0x342d0..0x342fc = 0
```

**eth0 默认在 XMAC1 上，是 eth 驱动把 XMAC1 这根 lane 点亮的（SOPC ready=1）；
XMAC0 是 switch 驱动当“9132 的 CPU 口”用的，那根 lane 从来没 ready 过。**
这与 52.1 完全吻合：XMAC0 收得到帧（MAC 核活着），但**帧交不到内部交换/IDM**。

**把 SOPC 双工字 0x343f0 写成 0x30（两位都置上）没有任何变化**——排除。

### 52.3 模块参数在运行时是可写的（之前的 EACCES 是路径被串坏了）

```
-rw-r--r-- 1 root root 4096 zx279133_eth0_xmac
-rw-r--r-- 1 root root 4096 zx279133_tx_port
echo 0 > .../zx279133_eth0_xmac   -> W1=0
echo 5 > .../zx279133_tx_port      -> W2=0
```

而且 `zx279133_idm_rx_parsed()`（idm.c:372）是**每帧现读** `zx279133_tx_port` 的，
所以 tx_port=5 立刻生效。**tx_port=5 生效后帧仍然进不了 IDM**⇒ 不是端口过滤。

### 52.4 内核命令行既不是 DTB 的，也不是 env 的

U-Boot 提示符上实测：

```
bootcmd=mtd read kernel 0x88000000; mtd read dtb 0x88800000; bootm 0x88000000 - 0x88800000
bootargs=console=ttyAMA0,115200n8 root=/dev/mtdblock5 rootfstype=jffs2 printk.time=1 U-Boot 2.0.0 20250417161359 0x200000 0x0 0x83 0x83 UpModeInfo=0x00000040 regioncode=0x0
```

**flash env 里的 bootargs 是原厂那一串，内核拿到的是另一串**
（DTB 的 /chosen/bootargs 去掉两个 module 参数之后的样子）。
两次 RAM 启动（21:31 env 里有旋钮、21:52 DTB 被打了补丁并用 `fdt print /chosen`
验证过旋钮在树上）**内核命令行里都没有旋钮**，而两个参数停在默认值，
并且**没有** “Unknown kernel command line parameter” 的告警。

**结论：这一版内核上，走命令行的路走不通；参数只能在运行时写。**

### 52.5 这一轮派 CI 包：加 `xpcs` 调试动词

§51.8 的实验 A（把原厂 `VEND2 AN_CTRL = 0x0005` 写回去）**卡在工具上**：
`m45` 动词只通到 `zx279133,outer-phy-bus`（np.c 里硬编码），**XPCS0 的寄存器根本够不着**。
但 switch 驱动自己**有** `priv->xpcs_mdiodev`（`zx279133_switch_xpcs_read/write`），
`zx279133-np.c` 里也有 `eth->xpcs_lan_mdiodev`（XMAC0 那根 lane 的 PCS）。

**所以这一版加一个动词**（`zx279133-np.c`，新写的 `xpcs`/`xpcsw`）：

```
xpcs  <lane> <devad> <reg>            读一个 PCS 寄存器
xpcsw <lane> <devad> <reg> <val>      写一个再读回来
lane: 0 = eth0 那根 lane 的 PCS（默认 XMAC1），1 = LAN lane 的 PCS（XMAC0 的）
```

**一个包只回答一个问题：把原厂那两个 lane 配置原样写回去，RX 会不会通。**

### 52.6 预登记：拿到这个包之后怎么走（判据全部写死）

0. **基线（正控制）**：`xpcs 1 0x1e 0x8001`（LAN lane 的 VEND2 AN_CTRL）
   与 `xpcs 1 0x1e 0x10`（PCS DIG_CTRL2）先**读出来抄一份**；
   `reg 0x90` 记下当前值（**0x2c03**）；XMAC0 的 RX 计数器（0x2400）读一次。
1. **实验 A（单变量）**：`xpcsw 1 0x1e 0x8001 0x0005`（原厂 AN_CTRL），
   再读 `reg 0x90`。**判据：链路字回到 0x38xx ⇒ 就是这一位**；随后打一组 PC 帧，
   **RX 计数器（0x2400）动了 ⇒ RX 通了**。
2. **实验 B（单变量）**：按 §51.6 的 USXGMII 配方改 lane——
   `xpcsw 1 0x1e 0x8000 <DIG_CTRL1: USXG_EN(BIT9)|VSMMD1_EN(BIT13)>`、
   `xpcsw 1 0x1e 0x8007 <KR_CTRL 清 GENMASK(12,10)>`、
   `xpcsw 1 0x1e 0x8000 <DIG_CTRL1 置 VR_RST(BIT15)，轮询到清零>`、
   `xpcsw 1 0x1e 0x8001 <AN_CTRL 置 AN_INTR_EN>`、`xpcsw 1 0x1e 0x1f 0x3140`（BMCR），
   同时 `regw 0x140000 0x20010001`（XMAC0 速度字 3→0 = USXGMII）。
   **判据同上：链路字 0x38xx + RX 计数器动。**
3. **实验 C（若 A/B 都 FAIL）**：`xpcsw` 把 XPCS0 的 **PCS mode** 改成工厂值，
   并且查 `spc` 表里 XMAC0 的端口属性（`r 5 <n>` 与 `r 6 <n>` 对比）。
4. **正控制（每轮都要做）**：PC 必须继续收到帧（`PC rx_bytes` 增量 > 0）；
   **不动就是仪器坏了，不是板子坏了**。

### 52.7 这一轮顺手修掉的工具坑

1. **`grep 'nppt +0x343f0'` 找不到东西**：偏移是**补零到八位**打印的
   （`nppt +0x0343f0`）。§51 之前对 0x342a4/0x342a8/0x342c0/0x342c4 的“读不到”
   就是这个原因——**它们其实读得到**，先前判成“读不到”是一次假阴性。
2. **`eg 0x27 <n> 32` 会被拒**（`ash: write error: Invalid argument`），
   而 `eg 0x19 0 32` 可以（读出 0x07000000，即 reason 0 → queue 7，队列号在 bit26:24）。
   **outport 表（0x27）暂时读不了**，这是一个待补的工具缺口。
3. **`u` 流会吃掉排在它后面的任何命令**（§51.7 已记），所以每个窗口一开始
   就要先把 `u` 流停掉再发命令；抓提示符那一下除外。
