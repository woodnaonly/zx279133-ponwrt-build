# 实机验收、备份与串口回退

**当前没有可执行的已验证串口回滚流程，也没有可刷 bootweb 镜像。** 下面是后续实测的顺序和记录要求，不是已经通过的验收报告。不得用原始 boot.bin、未验证的执行地址或旧脚本代替已知良好的救援链。

## 已知现场情况

设备为 SK-D840N / ZX279133，512 MiB RAM、256 MiB SPI NAND。通过当前 Linux 只读访问确认过社区 `svn308776` stage2 的哈希及当前 240 MiB root + 1 MiB scratch 布局。这不等于验证了 U-Boot 中的 NAND API。

2026-11-02 已通过 SSH 在设备 Linux 用户态运行同一份 C 校验核心和 HTTP 服务，完成真实固件上传校验、10 次上传中断和写入/重启锁定检查。测试只读打开 boot、tags，退出后保护区哈希一致，临时进程和文件已清理。详见 `../reports/2026-11-02-ssh-readonly.md`。2026-11-03 的原生 U-Boot RAM 和 ECC 试验另见 `../reports/2026-11-03-ttl-ram-readonly.md`；两份报告都不代替 Reset、前级救援及写入门槛。

现有 Linux 日志出现 JFFS2 数据 CRC 告警；即使 bad_blocks 和 ecc_failures 为 0，也不能声明存储完全正常。实机升级测试前需要保留这些告警及现有数据，不应先格式化根分区来消除现象。

2026-11-03 的 TTL 试验使用 `host/uart.py` 单进程独占 COM3，不启动旧 relay。不得抢占端口、启动第二个发送者、终止未知进程，或创建 `serreset` 文件（旧 relay 会切换 DTR/RTS）。需要检查历史 relay 状态时，应在正确目录运行，因原工具部分路径相对工作目录：

```powershell
Set-Location 'C:\UGit\openwrt\SK-D840N'
& 'C:\UGit\openwrt\SK-D840N\tools\relayctl.ps1' status
```

这条命令只读。实际发送任何串口内容前仍需确认唯一发送者、设备所处阶段与测试窗口；旧脚本里的 SSH 关闭主机密钥验证选项不能照搬。

本轮 RAM 只读例外只开放 TTL 装载和临时 `?` 别名接入，不开放任何持久化能力。最小探针和修复后的完整只读服务已返回 U-Boot，核对恢复入口、缓存、RX 回调和保存的驱动状态。此前首次完整服务在自校验中发生对齐异常并被厂商处理器自动重启，未进入 NAND 读取。不能把该重启计为自然供电周期，也不能据此延后智能开关的截止时间。同周期重复启动曾发生网络失败，仍未通过可重入测试。详细状态以 `../reports/2026-11-03-ttl-ram-readonly.md` 和对应原始日志为准。

## 实机门槛顺序

| 阶段 | 必须留下的证据 | 当前状态 |
| --- | --- | --- |
| 运行基底身份 | 当前 NAND stage2 哈希、串口 banner、只读分区表 | Linux 只读部分确认；非 RAM 验收 |
| RAM 命令接入 | 实际 DRAM 范围、gd/x18、重定位量、SP、返回 U-Boot 的日志 | 本机 RAM 只读入口已实测；不代表前级救援 |
| RAM 安全放置 | U-Boot、堆、栈、DTB、DMA、上传和 scratch 缓冲区互不重叠 | 本轮固定布局及 64 KiB 私有栈已核对；不是通用地址证书 |
| 2.5G 网络 | 指定物理口、MAC、ARP、ping、HTTP、完整上传、长时稳定和断连 | 原生网页及上传在 MAC 4 / 1000M 通过；2.5G、长时稳定未通过 |
| NAND 只读 | 几何参数、BBT、ECC、全长度读取、保护区与完整分区两次哈希 | 本轮仅 boot/tags 同路径 ECC 重复读取及坏块查询通过；未导出所有分区 |
| 看门狗与熵源 | 擦除/长哈希期间持续服务；token 熵源；网络故障后的行为 | 电脑安全随机 token、厂商已关闭看门狗的只读核对通过；主动喂狗/擦写未测 |
| Reset 入口 | 冷上电时按下/释放/极性及连续 3 秒实测；短按不得误触发 | 仅时间逻辑单测通过 |
| 前级救援 | 当前硬件安全分支、串口装载已知良好 U-Boot 并返回可用命令行 | 未完成，禁止启动区更新 |
| 完整备份 | RAM 环境导出的所有分区、配置、坏块/读取策略及本机独立校验 | 未完成，旧备份不能顶替 |
| 系统更新 | 正常升级、失败、断连、损坏系统后重新进入恢复页及重启 | 未完成 |
| U-Boot 更新 | 仅固定主程序窗口；保护区前后哈希相同；重启可用 | 未完成 |
| 常驻入口 | 冷启动、Reset、串口命令，系统不可启动时仍能进入 | 未完成 |

Reset、前级串口装载与掉电条件需要现场操作。硬件状态与串口协议尚未确认时，不把“准备好了串口线”算作 `BW_CAP_SERIAL_RESCUE`。

## 首次启动区写入前的备份

必须先有经过验证、无需当前 root 文件系统的 RAM 环境，然后备份当前设备，而不只是保留原厂 dump：

1. 记录启动源、完整分区表、NAND 几何参数和坏块清单。明确每个 dump 是物理偏移 ECC 读取、跳坏块逻辑流，还是 raw/OOB；不同形式不得混用恢复。
2. 导出完整 boot、kernel、dtb、parameter tags、root、scratch（或当时真实的每个分区）。保留 env、MAC/校准/序列号等原厂数据，不用其他设备的参数顶替。
3. 另存系统配置与权限/所有者信息、网络配置和救援所需的已知良好镜像。配置备份不能只剩包哈希。
4. 在 RAM 环境再次读取保护区并核对，在电脑上对每个备份校验长度和 SHA256；保留读取工具、错误/ECC 日志与时间。对有告警的介质不能只读一次就认定备份可靠。
5. 备份至少保留一份不在设备 NAND 上的副本。将本次实测证据与基底代码哈希绑定，由适配代码审查后才开放相应能力，不接受网页上传一份 JSON 自行解锁。

旧 `backups` 对照文件和 Linux 下的只读 dump 有分析价值，但不满足“当前完整分区及配置从 RAM 环境备份”的门槛。

## 回退分支

### 系统损坏但 U-Boot 仍可运行

先尝试经过验证的 Reset 或串口恢复入口。没有常驻入口时，使用已验证的 TFTP/RAM 救援 Linux；不要启动依赖损坏 root 的刷写工具。RAM 环境中核对实际布局和基底，再通过同一 ECC/坏块策略恢复系统，写入顺序仍为 root、dtb、kernel。每项都读回，再重启验证。

目前只验证了 bootweb 的 TTL/RAM 只读链，TFTP 救援启动、真实系统恢复、完整备份及读回重启尚未组成一条实测链，所以这里没有给出可直接复制的刷写命令。

### U-Boot 主程序损坏

先进入保留的前级 BTL，确认本机实际采用直接执行还是安全容器分支。使用本机实测过的串口协议和已知良好载荷启动 U-Boot/RAM 救援，不向未知地址试写；不要尝试通过关闭硬件安全状态来让未经验证的容器运行。

RAM 环境下先核对 BTL、env、boot 尾部和 parameter tags 与本机备份一致。恢复仅限 `[0x20000,0x180000)` 的主程序，采用已验证的 ECC、坏块与启动装载边界。**不能整分区擦除 mtd1**，因为那会一起擦掉前级和环境变量。

本机前级串口救援尚未实测，当前不承诺此分支一定可用，也不承诺自动回滚。若前级自身损坏，通常已超出这一软件回退方案，需另行确认硬件救援手段。

### 任何擦写失败

保持供电，停止自动重试；保存最后阶段、错误、坏块和读回记录。程序不得报告成功，也不得因浏览器重新连接而再次擦写。保护区检查不通过或无法读取时，应按严重失败处理。具体回退由仍可运行的已验证 RAM/串口链决定，不以盲目重启代替诊断。

## 每次启动区更新后的记录

记录 BTL `[0,0x20000)`、env `[0x180000,0x1A0000)`、boot 尾部 `[0x1A0000,0x200000)` 和整个 tags `[0xB00000,0xF00000)` 的更新前后 SHA256，确认字节未变。再记录新 stage2 哈希、冷启动 banner、Reset 进入、网络恢复页和系统启动结果。只有读回和重启均通过的确切构建，才可单独标记为可刷版本。
